**Harvested from:** `cathrynlavery/diagram-design` v2.4 (MIT) @ `09df49d8` — see `hermes_diagram_design_integration.md` for the full provenance record
**Applies to:** architecture documentation, adversarial/security review, Research Operating System visualization

---

## 0. The one rule that outranks everything

**A diagram is a PROJECTION. It is never authoritative state.**

Authority hierarchy (lowest wins nothing — it only *documents*):

```
executable Hermes behavior / persisted state
        ↓
ratified architecture / IDRs
        ↓
tests / executable contracts
        ↓
diagrams
```

- A diagram must never introduce a state that does not exist, an authority that does not exist, a transition that is not legal, a component inferred from vague prose, a dependency not supported by the repository, a new gate, a new scheduler, or a new evidence path.
- If a diagram conflicts with code or ratified architecture: **code wins, the diagram is wrong, fix the diagram.**
- Never modify Hermes behavior to make a diagram aesthetically consistent.
- Do NOT create `DiagramService` / `DiagramScheduler` / `DiagramAuthority` / `DiagramGraphDatabase` / `DiagramRepository`. Diagrams are hand-authored or generated by an ordinary script at review time; nothing in `src/hermes` imports diagram code.
- A diagram is done when the reader can trace every node and edge to a verified source (see §7 provenance manifest). No verified source → mark the node `DESIGNED` / `DEFERRED` / `UNVERIFIED` — never draw it as real.

## 1. Semantic pattern first, visual type second

Never pick a diagram type because it "looks nice". Ask: **what behavior is the reader trying to understand?** Then route pattern → type.

### Hermes routing table

| The reader must understand… | Semantic pattern | Visual type | Hermes examples |
|---|---|---|---|
| Who may mutate what | **Secure paved road** (trust boundaries, permitted vs forbidden ingress) | Architecture | Agent → Intent → Gateway → Repository → State; provider → hazard boundary → artifact |
| Why two similar requests diverge / what rejects what | **Paired policy-evaluation traces** (PASS/FAIL/SKIPPED/NOT-REACHED + first divergence) | Flowchart | one-verdict gate APPROVED vs REJECTED; gate resolve matrix |
| Ordered behavior after a crash | **Sequential recovery** (time-ordered steps, stale-write rejection) | Sequence / Flowchart | NO_SIGNAL → FAILED → requeue → re-execute; late handler discarded by fence |
| What states can a thing occupy + guards | **State transition with guards** | State machine | task lifecycle; ladder rungs (SUPPORTED/REFUTED terminal) |
| Where an artifact comes from / where it lands | **Unstructured input → structured artifact** + provenance | Data flow | provider content → hazard verdict → artifact + provenance edges |
| What depends on a failed claim | **Impact fan-out** | Tree / Architecture | Q-04 failure cone; blast radius |
| Which policy path rejects an input | **Policy evaluation** | Flowchart | gateway admission refusals (GATE/OPERATOR/TRANSITION/RATIONALE) |
| How the research process feeds itself | **Reinforcing loop with shared state** | Loop | ResearchProgram → … → Q-02 → dispatch |
| How a program becomes evidence | **Stage framework with semantic slots** | Process | pipeline: program → tasks → evidence → ladder |
| Who has which permission | **Access matrix** | Security matrix | operator credentials; S16 scope-review surface |

Use ONE primary pattern per figure. A second pattern may supply at most one supporting primitive; if both need full treatment, split into overview + detail.

## 2. Visual types (27) — condensed index

Architecture · IT current-state · Flowchart · Sequence · State machine · ER/data model · Timeline · Swimlane · Quadrant · Radar/spider · Loop · Nested · Tree · Org chart · Layer stack · Venn · Pyramid/funnel · Bar · Line · Gantt · Scatter · High-level · Process · Medallion · Data flow · DP integration · DP security matrix

Rules of thumb:
- If a 3-column table communicates the same thing, pick the table.
- If two types seem useful, pick the dominant axis.
- Above 9 primary nodes it is probably two diagrams (overview + detail).

## 3. Output model

- **Default: standalone static HTML with inline SVG.** HTML is the source of truth; SVG/PNG are derived exports — never hand-author an SVG as the primary artifact.
- Four dials set BEFORE drawing: **format** (`html` default), **size** (`doc-inline` default), **detail** (`balanced` default), **audience** (`mixed` default).
- Motion is optional (`none` default; `reveal`/`step`/`loop` only when requested or materially clarifying). Motion never changes static meaning.
- Every label and outcome must be complete in a static frame — the diagram must make sense with motion off and in grayscale.

---

## 4. Design rules (grayscale-safe by default)

- **Density target 4/10.** Done when nothing can be removed, not when everything is added.
- **1–2 focal nodes max** (coral/editorial emphasis). Using emphasis on 5 nodes erases the signal.
- **Never use color as the only semantic mechanism.** Every meaning must survive grayscale: use line style (solid = primary/authorized, dashed = optional/async/forbidden), stop symbols (X / ⊘), shapes, and text labels in addition to color.
- Orthogonal (right-angle) connectors are mandatory; diagonal connectors between off-axis nodes are a hard fail. Bridge (hop) the *less* important arrow at crossings, never both.
- Zones (trust boundaries, tiers) as dashed rounded rects with a paper-colored label mask on the boundary line.
- No node represents two ideas; no connection is drawn when layout already implies it.
- Text: readable at target size, ≤2 lines per label. When a cell needs prose, move prose to notes.

## 5. The four Hermes modes

### 5.1 Architecture mode
For any architecture review (v6/v7 amendments, provider, task graph, gateway, provenance, Evidence Ladder, agent/tool boundaries, Engineering Plane). Every component must carry: source file, owning module, authority, read/write capability, relevant contract. Encode status visually where useful: `IMPLEMENTED` solid, `DESIGNED` dashed outline, `DEFERRED`/`UNVERIFIED` muted + labeled.

### 5.2 Authority / trust-boundary mode
Answer: **who is allowed to mutate what?** Distinguish explicitly: authority, advisory capability, data, persistence, external/untrusted content. Draw the forbidden path so it *visibly stops* at the boundary (X + label), never rejoins the approved route.

### 5.3 Adversarial review mode
Visualize attack paths, not just happy paths:
- attacker-controlled input → parser → validation → write boundary → state, with the precise control point highlighted;
- bypass path (agent → direct repository call, expected gateway) with the missing hop crossed out;
- recovery attack (controller A lease loss → controller B reclaim → stale A write ✗ generation fence).

### 5.4 Research Operating System mode
Visualize the loop as a Loop figure with exactly one hub (the shared accumulating record — the task graph / event journal) and 5–8 stations. Label every station `IMPLEMENTED` / `PROPOSED` / `DEFERRED`. This is a conceptual visualization of existing/proposed capabilities — it must NOT create a second lifecycle model, a second scheduler, or any authority.

## 6. Before drawing — collect the source facts

For every diagram maintain a provenance manifest:

```text
diagram source:
  repository commit            # Hermes HEAD the diagram was verified against
  files inspected              # code files, with line refs where possible
  architecture documents       # hermes_*.md, IDRs
  tests                        # the tests that pin each behavior
  external skill               # cathrynlavery/diagram-design @ commit, v2.4, MIT
  status of each node          # IMPLEMENTED / DESIGNED / DEFERRED / UNVERIFIED
```

A diagram without a manifest is a sketch, not a Hermes artifact.

## 7. Anti-patterns (harvested + Hermes-specific)

- Dashed box called "security" with no route semantics.
- Forbidden arrow crossing INTO the protected zone; a bypass path that visually rejoins the approved route.
- Green/red dots without words; color-only semantics.
- "AI magic" sparkle between two boxes; fields appearing without sources.
- Two independently ordered flows compared as if paired; treating SKIPPED as NOT-REACHED.
- Drawing components that exist only in a design doc as if they were implemented.
- A diagram that shows a state Hermes cannot reach, a transition the state machine refuses, or a second scheduler.
- Animation that changes item order or hides the static answer.
- Adding a Hermes subsystem to render diagrams.

---

## 8. Verification loop

1. Draw only from verified facts (§6).
2. Cross-check every edge against the code path it claims (grep the symbol).
3. Check the diagram against the state machine / gateway / fence contracts.
4. If a conflict surfaces, the conflict is a FINDING: code wins; fix the diagram and record the discrepancy.
5. Regenerate/re-check whenever the reviewed surface changes (same discipline as the Ix refresh).
