# IDR-014: Backup Implementation — SQLite Online Backup API

**Status:** Decided (Phase 1)
**Date:** 2026-08-10
**Decides for:** How database snapshots and restoration work.

## Context

v3 §16.4: snapshot after gates and at completion; `sqlite3 .backup` or
`VACUUM INTO`; verification by `PRAGMA integrity_check`. Phase 1 req §15:
integrity check, safe snapshot, configurable backup destination, restoration
test.

## Decision

**SQLite Online Backup API** (`sqlite3.Connection.backup()`).

### Why the Online Backup API
- Available in stdlib `sqlite3` (no external dependency).
- Safe to run while the database is in use (WAL mode allows concurrent
  readers during backup).
- Produces a byte-for-byte copy of the database — WAL and journal included.
- No need to close connections or stop operations.

### Backup procedure
1. Open a new connection to a destination file.
2. Call `source_conn.backup(dest_conn)` — copies all pages.
3. Close the destination connection.
4. Run `PRAGMA integrity_check` on the destination file.
5. If integrity check passes: log success, record backup metadata.
6. If integrity check fails: delete the backup file, log error, raise.

### Restore procedure
1. Close all connections to the live database.
2. Copy the backup file to the database path.
3. Reopen the database connection (migrations verify schema version).
4. Run `PRAGMA integrity_check`.
5. If integrity passes: restore complete.
6. If integrity fails: raise, do not use the corrupted restore.

### Configuration
- `backup_dir` (from config, default "backups") — backup destination directory.
- `retain_last_n` (from config, default 5) — keep the N most recent backups,
  delete older ones.
- Backup filename: `hermes_backup_<timestamp>.db`.

### Phase 1 acceptance
- A database with state can be backed up and restored.
- The restored database contains the same authoritative state and the
  complete event journal.
- `PRAGMA integrity_check` passes on the restored database.

## Revisions

None.
