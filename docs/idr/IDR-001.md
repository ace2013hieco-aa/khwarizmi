# IDR-001: Dependency-Management Tool — `uv`

**Status:** Decided (Phase 0)
**Date:** 2026-08-10
**Decides for:** How Hermes reproducibly resolves, locks, and installs dependencies.

## Context

Foundation decision §3 mandates `pyproject.toml` + a committed lockfile for reproducible environments, a modern standards-compliant tool, and explicitly warns against choosing Poetry merely out of familiarity or introducing a framework for scaffolding alone.

## Decision

Use **uv** (Astral) for: virtual-environment creation, dependency resolution, lockfile generation (`uv.lock`), and reproducible `uv sync` installation.

## Rationale

1. Standards-based: reads `pyproject.toml` per PEP 621; generates a single `uv.lock` cross-platform lockfile.
2. Supports `[dependency-groups]` (PEP 735) and `[project.optional-dependencies]` cleanly.
3. Extremely fast Rust resolver — we are not adopting a Rust *core* for Hermes, only this tool.
4. Minimal ceremony: no `poetry-core` build-system coupling; we still use `hatchling` as the build backend.
5. Installed and proven in this environment already (`uv=installed` per environment audit).

## Alternatives Considered

* **Poetry** — capable, but adds `poetry-core` coupling and `poetry.lock` (a second ecosystem). Foundation §3 warns against it.
* **Pip + requirements.txt** — has no lockfile (only a requirements list); does not support `[dependency-groups]`.
* **Rye** — predecessor of uv; now united under uv.
* **Hatch alone with no separate resolver** — Hatch is the build backend (see IDR-002); it depends on pip or uv for resolution and lacks a standalone committed lockfile standard.

## Consequences

* `uv.lock` is committed; `uv sync` reproduces the environment exactly.
* Developers need `uv` installed. `README.md` documents install steps.
* `pyproject.toml` uses `[dependency-groups]` (PEP 735) for dev deps.
