# IDR-006: Phase-0 Sandbox Default — Disabled

**Status:** Decided (Phase 0)
**Date:** 2026-08-10
**Decides for:** The default state of the `sandbox` configuration section in Phase 0.

## Context

Foundation §10 lists "sandbox availability" as a `hermes doctor` probe that must distinguish `AVAILABLE` from `OPTIONAL / NOT CONFIGURED`. Foundation §5 names a sandbox isolated behind `SandboxedPythonTool`. v3 §18 calls the execution sandbox untrusted and isolated (T4 boundary) — but the actual tool runtime (Phase 5) and the sandbox integration are not Phase 0 deliverables.

## Decision

The default `config/hermes.toml` ships with `sandbox.enabled = false` and `sandbox.runner = ""`. `hermes doctor` reports `OPTIONAL / NOT CONFIGURED` for the sandbox in Phase 0.

## Rationale

1. Phase 0 is foundation-only (no tool runtime; no code execution). Enabling sandbox configuration would imply a capability the system does not yet have.
2. Surfacing sandbox status as OPTIONAL (rather than REQUIRED/MISSING) honors foundation §10's directive not to treat every absent external capability as an installation failure.
3. Operators who wish to pre-configure a runner (e.g., for later Phase 5 testing) can flip `enabled = true` and set `runner = "docker"` (or similar); `hermes doctor` will then probe PATH for the runner and report AVAILABLE/MISSING accordingly.

## Alternatives Considered

* **Default `enabled = true` with `runner = "docker"`** — would produce a spurious REQUIRED/MISSING or error on systems without Docker, misrepresenting Phase-0 capabilities.
* **Omit the sandbox section entirely** — loses the explicit boundary that this capability exists and is deferred.

## Consequences

* `hermes doctor` reports `Sandbox: [OPTIONAL / NOT CONFIGURED] — disabled in config` at Phase 0.
* Phase 5 will flip the default or document the operator step; a new IDR will be recorded if the boundary or probe semantics change.
* No sandbox-dependent tests run at Phase 0; all tests are pure-Python and stdlib-only.
