# IDR-011: Timestamp Representation — UTC ISO-8601 with Microsecond Precision

**Status:** Decided (Phase 1)
**Date:** 2026-08-10
**Decides for:** How timestamps are stored and compared in Hermes.

## Context

Phase 1 req §2: deterministic timestamps where tests require them. v3 §8.1:
events need creation timestamps for audit ordering. v3 §7: task
created/started/completed timestamps.

## Decision

**UTC ISO-8601 strings with microsecond precision**, stored as `TEXT` in SQLite.

### Format
```
YYYY-MM-DDTHH:MM:SS.ffffff+00:00
```
Example: `2026-08-10T19:50:50.123456+00:00`

### Rationale
- **UTC**: eliminates timezone ambiguity. Every timestamp is comparable via
  lexicographic string ordering (`TEXT` sort in SQLite == chronological sort
  for same-format ISO-8601 UTC).
- **Microsecond precision**: sufficient for event ordering within a single
  transaction (events appended in the same `BEGIN...COMMIT` still get
  distinct timestamps if called in sequence).
- **ISO-8601**: standard, human-readable, machine-parseable, no external deps.
  `datetime.fromisoformat()` in stdlib handles it natively (Python ≥3.11).

### Deterministic test timestamps
- The timestamp source is a `now()` function that returns
  `datetime.now(UTC)`.
- Tests inject a frozen clock (a callable returning a fixed timestamp) to
  achieve determinism. The production code never calls `datetime.now()`
  directly — it uses the injected clock.

### SQLite TEXT storage
- SQLite has no native datetime type; `TEXT` with ISO-8601 is the
  recommended approach (per SQLite docs) and gives correct sort order.

## Revisions

None.
