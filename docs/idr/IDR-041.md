## Context

The proposal lifecycle (IDR-040 §3.5) ends with a ratified verdict. The
handoff question — where the APPROVED verdict goes — is answered by the
design gate: every `PermittedAction` already maps to an existing Hermes
authority path, so the approval is **evidence-of-ratification** for those
paths, consumed through a `ratification_ref` input contract (AC-4). This
IDR ratifies the contract and the first two consumers. It does NOT create
an executor: no approved-proposal auto-execution ladder is architecture
(the same rejection as the auto-retraction ladder in IDR-040 §4 — a
ratified fact is not a trigger).

## 1. The ratification-ref contract (AC-4, ratified verbatim)

A `ratification_ref` (a `ClassificationActionProposed` correlation id)
dereferences to a ratified human approval **iff**:

1. the proposal event exists in the same project;
2. a `ClassificationActionDecision` event for it records **APPROVED**
   (a REJECTED or undecided proposal never ratifies);
3. the proposal's action is in the CONSUMER's allowed action set;
4. the action is in the classification's `permitted_actions` set
   **recomputed** from the dereferenced class (F2 — never the stored
   state, never the stored permitted list; a missing/corrupt
   classification never ratifies).

Any failure returns `None` and the consumer refuses fail-closed with the
`PROPOSAL` code. The contract is enforced by the shared
`_resolve_ratified_proposal` gateway helper — one implementation, both
consumers.

## 2. Consumer one — the S16 scope-review intake

`RECORD_SCOPE_REVIEW_DECISION` (internal-only, DETERMINISTIC — the human
has no agent profile; the deterministic layer ingests the operator verdict)
is the S16 intake: it records the human's scope verdict on an APPROVED
S16-routed proposal, appending the append-only `ScopeReviewDecided` event
(`correlation_id = proposal_id` — the ratification ref IS the correlation).

- **Admission contract:** the `proposal_id` must satisfy AC-4 with the
  S16-routed action set (`ROUTE_TO_SCOPE_REVIEW`, `PROPOSE_SCOPE_NARROWING`);
  the `scope_decision` must be a ratified `ScopeReviewDecision`
  (`CONFIRM_SCOPE` / `AMEND_SCOPE` / `DEFER_SCOPE`); unknown keys rejected;
  rationale capped.
- **ONE SCOPE DECISION PER APPROVAL:** an identical re-record is
  idempotent (`duplicate=True`); a second DIFFERENT scope decision on the
  same approval is refused (`PROPOSAL`) — nothing written.
- **Lease-held ingestion:** `Controller.record_scope_review_decision` is
  the sanctioned surface — it builds the intent and admits it through the
  gateway under a held scheduler lease (a concurrent controller's lease
  refuses the record fail-closed with code `LOCK`; the lease is released
  after). Rejections are surfaced as data, never raised through the loop.
- **Boundary:** the record is evidence-of-ratification for the S16
  authority's SEPARATE, versioned brief amendment — nothing here amends a
  `scope_briefs` row and nothing executes (fixture-pinned: zero brief
  writes).

## 3. Consumer two — EVIDENCE_TRANSITION with the AC-4 contract

`EVIDENCE_TRANSITION` (LLM-proposable, the branch-transition authority) is
now wired as a **proposal-shaped admission** (the IDR-040 precedent): the
gateway validates the transition shape and emits `EVIDENCE_TRANSITION_`
`PROPOSED` — the audit IS the record; APPLYING the transition (changing
evidence state) remains the future Evidence Ladder's authority, and the
admission changes no state.

- **Shape validation:** the evidence ref must dereference in-project
  (`evidence:<artifact_id>`, new `EVIDENCE_REF` rejection code); `from_state`
  / `to_state` must be ratified evidence states (`SUPPORTED` / `ROBUST` /
  `REPLICATED` / `REFUTED` — the ladder rungs + the v6 §10.2 terminus);
  a transition must change state and may not leave `REFUTED` (the
  terminal); rationale capped; unknown keys rejected.
- **The ratification-ref contract (AC-4):** when a `ratification_ref` is
  carried, it must be an APPROVED **REJECT_BRANCH** proposal whose action
  is in the classification's permitted set (recomputed, F2); a ref to a
  REJECTED/unknown proposal, a non-REJECT_BRANCH approval, or an action
  outside the class's permitted set is refused (`PROPOSAL`) — nothing
  written.
- **Idempotent** via a deterministic transition id (`tr_<hash>`): repeat
  admissions duplicate nothing.
- **Reachability (RESOLVED by the authority decision, ratified below):** the
  authority model now routes branch rejection to human confirmation — the
  proposal gate is ACTION-shaped, so `REJECT_BRANCH` is admitted
  PENDING_HUMAN_APPROVAL for ANY class (including the one class that owns
  it, `DECLARED_CONSTRAINT_VIOLATION`), and a legitimately-APPROVED
  REJECT_BRANCH proposal is reachable end-to-end through the gate — the
  chain that feeds the APPLY pass's REFUTED driver. The refusal paths
  (REJECTED / unknown / action-mismatch / class-mismatch) remain live.

## 4. Authority boundary

- **CAN** surface/record the ratification consumption: the scope decision
  record and the transition proposal are append-only audit records.
- **CAN** carry a `ratification_ref` into an existing path's admission as
  evidence — the AC-4 contract, enforced by the shared resolver.
- **CAN** APPLY a ratified transition — the Evidence Ladder APPLY pass is
  the ladder's ONLY write path, driven only by ratified facts (§6).
- **CANNOT** execute anything outside the APPLY pass: no brief amendment,
  no task/artifact mutation, no auto-routing; the admission never applies
  and the APPLY never accepts a bare agent claim. A ratified fact is not a
  trigger — it is the APPLY's input.
- **CANNOT** bypass existing validation: the ref is an input, never a
  skip-switch; each admission still validates its own domain inputs.
- **CANNOT** create a second decision or scope record: the one-verdict and
  one-scope-decision rules are the lifecycle's terminality guarantees.

## 5. The per-action authority gate (the authority decision)

The design gate's open authority question — route branch rejection to
human confirmation so APPROVED branch transitions become reachable — is
**decided and ratified here**: the proposal gate is ACTION-shaped, not
class-only.

- `proposal_requires_human_confirmation(class, action)` — True iff the
  CLASS requires it (FRAMING_ERROR) OR the ACTION is authority-shaped
  (`AUTHORITY_SHAPED_ACTIONS` = `REJECT_BRANCH`, `ROUTE_TO_SCOPE_REVIEW`,
  `PROPOSE_SCOPE_NARROWING`, `PROPOSE_MECHANISM_SUBSTITUTION` — the AC-5
  leg, ratified this round: substituting a ratified program's mechanism is
  an authority act, so its approval must be REACHABLE as a ratification
  fact for the `PROPOSE_RESEARCH_PROGRAM` admission). Advisory actions
  (`REVIEW_DOWNSTREAM_IMPACT`, `PARK_FOR_RESOURCE_REVIEW`,
  `ESCALATE_TO_DIRECTOR`) stay EFFECTIVE.
- **F2 everywhere:** the admission gate, the pending-proposals replay, and
  the decision validator all RECOMPUTE the gate from the dereferenced
  class AND the payload action — never from the stored admission state.
  A proposal whose stored state contradicts the recomputed gate is a
  tamper signal: the class+action win (a tampered `EFFECTIVE → PENDING`
  replay is still replayed; a tampered `PENDING → EFFECTIVE` on a gated
  action is still decidable).
- **Consequence:** REJECT_BRANCH proposals are now admitted
  PENDING_HUMAN_APPROVAL for ANY class, decidable, and their approvals are
  real ratification facts — the reachability note in §3 is RESOLVED. The
  same now holds for PROPOSE_MECHANISM_SUBSTITUTION (ratified this round):
  the §7 by-design unreachability note is replaced by the reachability
  FACT — the AC-5 mechanism-substitution approval is decidable end-to-end
  through the gate, feeding the `PROPOSE_RESEARCH_PROGRAM` admission as
  ratified rationale evidence.

## 6. The Evidence Ladder APPLY executor (AC-1..5 ratified)

The APPLIED side the §5 deferred item pointed at is now architecture: the
deterministic executor that consumes the admitted `EVIDENCE_TRANSITION_`
`PROPOSED` records (and the recorded satisfaction links) and ACTUALLY
changes evidence state — the ladder's ONE write path. Contract (the design
gate's AC-1..5, ratified verbatim by the implementation):

- **Substrate:** `evidence_ladder_state` (migration 9→10) — one versioned,
  append-only row per (program, hypothesis): rung (`SUPPORTED` / `ROBUST` /
  `REPLICATED` / `REFUTED`, CHECK-enforced), the deterministic transition
  id that produced it, and the driver (`obligations` / `ratification`).
  No UPDATE/DELETE path; the row is the CACHE of a derivation, never the
  authority (F2).
- **AC-1 — obligation climbs:** the pass derives the highest rung whose
  artifact obligation set (`LADDER_OBLIGATIONS`) is satisfied by the
  recorded per-requirement satisfaction links (IDR-038 §3.1); completed
  obligations ARE the ratification — no agent intent. `SUPPORTED → ROBUST
  → REPLICATED` advances deterministically and idempotently, each emitting
  one `EvidenceTransitionApplied` with a content-derived `eltr_<hash>` id.
- **AC-2 — ratified REFUTED, both drivers (the deferred branch is now
  ratified, this round):**
  - *Driver 1 — proposal-shaped:* applied only from a RE-VERIFIED ratified
    input — the pass re-runs the AC-4 checks at apply time via the shared
    `_resolve_ratified_proposal` (APPROVED REJECT_BRANCH, action in the
    recomputed permitted set), dereferences the classification's
    (program, hypothesis) with the digest-valid identity discipline, and
    refuses a forged/stale/unratified proposal with an observable note —
    nothing applied.
  - *Driver 3 — bare-classification (the AC-2 deferred branch):* a
    digest-valid Q-05 classification ALONE certifies a DECISIVE
    falsification and applies terminal REFUTED — no transition proposal,
    no agent intent; the ratified classification record IS the
    falsification fact. The ratified falsification predicate
    (`certifies_decisive_falsification`, derived from the taxonomy, never
    a stored flag — F2): the class is `DECLARED_CONSTRAINT_VIOLATION`
    (the one falsification-shaped class; its action map is REJECT_BRANCH)
    AND the cited constraint is the hypothesis's OWN declared
    falsification condition (`hypothesis:<H>:falsification_condition`).
    A methodology-constraint violation is a process failure, never a
    falsification; every other class is explicitly NOT decisive.
    Fail-closed per row: a forged identity, corrupt metadata, a
    non-ratified class, a non-falsification citation, or an unresolvable
    foreign target applies nothing and is never a crash. The transition
    id is `classification_transition_id` — content-derived from the
    classification ref, so one falsification record applies at most once,
    deterministically, stable across replays. The write records
    `ratified_by="classification"` + the cited `constraint_ref` as
    provenance. F12 extends to driver 3: a cache tampered DOWN after an
    applied classification-REFUTED is healed with a note, never silently.
- **AC-3 — REFUTED is terminal:** no applied REFUTED is ever reverted; the
  admission refuses a transition leaving REFUTED; a cache showing REFUTED
  whose ratified input no longer re-verifies is observed, never reverted.
- **AC-4 — crash-recovery determinism:** every write is ONE transaction
  (row + event commit or roll back together); the derived rung and the
  deterministic transition ids are pure functions of ratified sources, so
  a crash mid-chain recovers to the identical ladder (multi-tick crash
  fixtures + identical-facts-different-schedules fixtures).
- **AC-5 — no bare-payload writes:** every write traces to a ratified
  source (satisfaction links / AC-4 binding); a declared-but-unratified
  transition proposal applies nothing.
- **F12 — tamper-heal semantics (ratified):** the cache is only ever
  COMPARED against the derived rung, never trusted. A cache tampered ABOVE
  the derivation is repaired to the true rung with an observable
  tamper-signal note (a repair emits no APPLIED event — it is not a
  transition); a cache tampered DOWN after a legit apply (the applied
  transition hidden) is healed the same way — the idempotency guard never
  silently swallows a hidden transition. REFUTED-terminal safety always
  wins over self-healing.
- **Read surface (digest v4, ratified this round):**
  `evidence_ladder_transitions()` — the applied transitions (the audit
  events), deterministic order, read-only; folded into the Director's
  `reconcile_digest` v4 (`ladder_transitions` section, content-hash
  bound). `bare_classification_falsifications()` — the applied
  BARE-classification REFUTED facts (payload `ratified_by ==
  "classification"`), the digest's `falsifications` section: refutations
  are visible in the daily digest, distinct from proposal-ratified
  transitions. `refutation_review_candidates()` — the Q-04 artifact blast
  radius seeded by EVERY applied REFUTED transition (proposal- or
  classification-ratified): the falsified hypothesis's evidence base (its
  satisfaction-linked artifacts + the falsification classification's cited
  evidence, when resolvable), every DOWNSTREAM artifact over
  `provenance_edges`, and the DEPENDENT hypotheses — the program's
  hypotheses that rival the falsified one (`rival_of == hypothesis_ref`),
  with their current ladder rung. The digest's
  `refutation_review_candidates` section carries the same set — the
  falsification FACTS and the re-review SET they demand are both in the
  one-call Director surface, read-only as ever, version-bound and
  content-hashed. Fail-closed: foreign targets and unresolvable
  classification refs contribute nothing, never a crash.
- **RefutedApplied — the falsification as a first-class event (ratified
  this round):** when the bare-classification driver applies terminal
  REFUTED, the SAME atomic write ALSO records a `RefutedApplied` event
  (same correlation_id as the `EvidenceTransitionApplied`, payload with
  program/hypothesis/classification/constraint refs) — event-catalog
  consumers subscribe to the fact directly, no ladder-row reads, no
  payload filtering. The `falsifications` digest section reads it.
  Obligation climbs and proposal-ratified REFUTED never emit it.
- **The Director's observe→act loop (ratified this round):**
  `propose_refutation_actions()` consumes `reconcile_digest()` and emits
  one `PROPOSE_CLASSIFICATION_ACTION` intent per DOWNSTREAM artifact of
  every applied REFUTED transition — the `REVIEW_DOWNSTREAM_IMPACT`
  review obligation (advisory-shaped, EFFECTIVE — no human gate) cited
  against the falsification's own classification, admitted through the
  gateway (D3 dereference + candidate existence re-validated),
  idempotent, proposal-only, with observable rejections. The ACTION still
  requires its existing authority — this loop only PROPOSES, closing the
  observe→act loop the digest v4 fold opened.
