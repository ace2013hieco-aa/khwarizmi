## P1 — SOURCE_FETCH must not cross project search lineage

The gateway resolved the cited search task (existence / SOURCE_SEARCH marker /
declared dependency) but never checked
`search_row.project_id == intent.project_id`. Under the global-content model
(`content_hash` UNIQUE + edge-carried project ownership), a Project-B fetch
can legitimately resolve Project-A-produced content, so the refs check could
not pin the lineage.

Enforced at both authoritative binding surfaces:

1. **Gateway admission** — a SOURCE_FETCH citing a search task of another
   project is rejected with the PROVENANCE code (`P1 lineage`), even when
   every ref dereferences.
2. **Write path** — `_validate_task_binding` (fetch branch) re-checks the
   producing task's `spec.search_task_id` inside the write transaction (the
   V6-P7-A2 discipline): exists, SOURCE_SEARCH, same project. A forged or
   stale row is refused at record time, never recorded against an ambiguous
   lineage.

## C1 — provider contract alignment

Admission allowed `provider=None` while `_run_fetch` requires a provider for
adapter routing — a provider-less fetch passed admission and failed at
execution. Closed from both ends: the gateway requires a non-empty
allowlisted provider (IDR-030); `build_source_fetch_task_payload` makes
`provider` required.

## Reviewed and accepted (documented in the remediation record)

- Fetch refs from a non-cited same-project search: the write path's A2-01
  refs match fails closed; a "refs must come from the cited search"
  admission rule would be wrong under the shared-content model.
- `load_search_results` task-keyed read surface: reachable only from an
  admitted fetch task whose lineage is pinned same-project at both binding
  surfaces.
