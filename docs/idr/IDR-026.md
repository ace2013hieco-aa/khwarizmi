# IDR-026: CONTRA P7 write path — persisting ResearchClaim / ResearchAssumption (repository, migration, dereference resolver)

**Status:** Decided — **DESIGNED**, now **IMPLEMENTED + TESTED** by IDR-027 (`src/hermes/persistence/migrations.py` migration 4→5, `ClaimAssumptionRepository` in `repositories.py`, 25 golden fixtures in `tests/test_claims_write_path.py`; authoritative suite 500 passed, 0 failed). **Audit-2 remediation (V6-P7-A2-01/02/03):** migration 5→6 adds `producing_task_id` (FK to `tasks`) on both artifact tables, and `record_extraction` now requires a producing task — verified inside the write transaction (exists, project match, EXTRACT marker, RUNNING — atomic with the write, closing the TOCTOU window) with one-shot acceptance per task (identical re-acceptance stays idempotent; divergent output is refused). Re-verified by the independent audit-2 probe script (5/5, 0 flagged); authoritative suite 539 passed, 0 failed. The extraction-task pipeline and `regime`/`methodology` dereference remain DEFERRED (Decision 6). The substrate it persists (`src/hermes/research/claims.py` + `tests/test_claims.py`) is IMPLEMENTED + TESTED (IDR-025).
**Date:** 2026-08-13
**Decides for:** How the advisory `ResearchClaim`/`ResearchAssumption` artifacts persist — schema (migration 4→5), the repository write contract, the dereference resolver over existing authoritative carriers, atomicity/idempotency, supersession, and the audit trail — **without adding any new event type, intent kind, scheduler, or authority** (§29.1 zero-new-authority rule; §29.2 rules 1/2/4/8).

## Context

IDR-025 landed the deterministic core: `ResearchClaim`/`ResearchAssumption` artifacts with content-derived identity (`cl_<sha256[:24]>` / `as_<sha256[:24]>`), a closed context-tag vocabulary (`CONTEXT_DIMENSIONS`), a `ContextResolver` protocol for authoritative dereference, and `validate_extraction` (the `ClaimAssumptionValidator`) — pure, no persistence, no events. The §29.3 amendment text says the write path must follow the GR1/GR5/S6 validation pattern: "Extraction proposed by LLM tasks (C-tier), admissibility decided by a deterministic `ClaimAssumptionValidator` … No new event; per-artifact provenance + §14 edges; LLM contributions `model_ref`-tagged, never authoritative lineage."

This record makes that text concrete. It answers: which tables, which repository, which resolver, what the transaction looks like, and what is deliberately deferred.

## Governing constraints (re-derived, not assumed)

1. **Zero new events, intents, schedulers, authorities** (§29.1) — the write path adds none of these. In particular, **no `ClaimExtractionAdmitted`-style event** is added to the §8.1 catalog.
2. **Never-evidence structural rule** (§29.2 rule 1, CT-R2, PA2/GR3 verbatim) — the persisted rows carry no ladder/validation surface; `dependent_claim_ids` is structural bookkeeping, never evidence.
3. **One-directional dependency** (§29.2 rule 2, CT-R3) — persisted assumptions can never bear obligations; the `research_programs`/`ExperimentSpec` machinery is untouched.
4. **Challenge authority limit** (§29.2 rule 4, CT-R4) — the write path performs admission only; it can never set challenge statuses or promote/refute anything.
5. **Manual-proof-first** (§29.2 rule 7) — this is the design that the future Part 3 implementation will golden-fixture before any scheduled execution.
6. **Trust model (Model D discipline, v6 §28.2)** — the validator (derivation authority) and the repository (governance + identity/integrity authority) stay separate; the repository re-derives identity with the same helpers rather than trusting caller-claimed objects, but never re-runs the epistemic validator.

## Decision 1 — Schema: migration 4→5, then 5→6 (forward-only, IDR-010)

Three tables, mirroring the `research_programs` pattern (content-addressed identity, `UNIQUE (project_id, content_hash)` idempotency, head-only supersession, `CHECK` self-supersede, no UPDATE/DELETE):

**`research_claims`**
```
claim_id          TEXT PRIMARY KEY,              -- cl_<sha256[:24]>, validator-derived
project_id        TEXT NOT NULL REFERENCES projects(project_id),
content_hash      TEXT NOT NULL,
statement         TEXT NOT NULL,
source_ref        TEXT NOT NULL,                 -- 'artifact_type:ref'
span_ref          TEXT,
claim_type        TEXT,
context_tags_json TEXT NOT NULL,                 -- closed CONTEXT_DIMENSIONS map
schema_version    TEXT NOT NULL,
extracted_by      TEXT NOT NULL,                 -- model_ref / task id (advisory provenance)
supersedes_id     TEXT REFERENCES research_claims(claim_id),
created_at        TEXT NOT NULL,
UNIQUE (project_id, content_hash),
CHECK (supersedes_id IS NULL OR supersedes_id != claim_id)
```

**`research_assumptions`**
```
assumption_id          TEXT PRIMARY KEY,         -- as_<sha256[:24]>, validator-derived
project_id             TEXT NOT NULL REFERENCES projects(project_id),
content_hash           TEXT NOT NULL,
statement              TEXT NOT NULL,
context_tags_json      TEXT NOT NULL,
supporting_artifact_refs_json TEXT NOT NULL,
status                 TEXT NOT NULL DEFAULT 'ACTIVE'
                       CHECK (status IN ('ACTIVE','SUSPENDED','SUPERSEDED')),
schema_version         TEXT NOT NULL,
supersedes_id          TEXT REFERENCES research_assumptions(assumption_id),
created_at             TEXT NOT NULL,
UNIQUE (project_id, content_hash),
CHECK (supersedes_id IS NULL OR supersedes_id != assumption_id)
```

**`claim_assumption_links`** — the authoritative normalized relation (the §29.3 `assumption_ids[]`/`dependent_claim_ids[]` made queryable):
```
claim_id       TEXT NOT NULL REFERENCES research_claims(claim_id),
assumption_id  TEXT NOT NULL REFERENCES research_assumptions(assumption_id),
UNIQUE (claim_id, assumption_id),
CHECK (claim_id != assumption_id)
```
- `dependent_claim_ids` on the artifact stays as a read-side projection of this table (deterministic, sorted — the validator's output); the **table is the truth**, satisfying "which assumptions does this claim depend on?" / "what breaks if assumption A fails?" as plain queries.
- Indexes: `(project_id)`, `(content_hash)`, `(supersedes_id)`, `claim_assumption_links(assumption_id)`.
- `SUPPORTED_VERSION` 4 → 5; `_MIGRATIONS` gains `_migrate_4_to_5`.
- `SUPPORTED_VERSION` 5 → 6 (V6-P7-A2-01); `_MIGRATIONS` gains `_migrate_5_to_6`: `producing_task_id TEXT REFERENCES tasks(task_id)` via `ADD COLUMN` (nullable — forward-only, no rebuild) on `research_claims` and `research_assumptions`, with per-table indexes. Every new write records the producing task; the FK is schema-enforced.

Rationale: a generic `artifacts` row could hold the bytes, but the §29.3 requirements (content-addressed identity, project-scoped idempotency, FK-enforced links, status CHECK, supersession edges, no-delete immutability) are exactly the `research_programs`-style typed-table guarantees. One table per artifact class is the house pattern (programs, scope briefs, manifests); the link table keeps dependency maintenance in the DB, not in JSON parsing.

## Decision 2 — Repository: `ClaimAssumptionRepository` (governance + integrity authority)

In `src/hermes/persistence/repositories.py`, mirroring `ResearchProgramRepository`'s contract:

- **`record_extraction(project_id, result: ExtractionResult, *, producing_task_id, extracted_by, reason="") -> ExtractionOutcome`** — `producing_task_id` is required (V6-P7-A2-01): the task must exist, belong to `project_id`, be an EXTRACT task, be RUNNING (re-checked INSIDE the write transaction — V6-P7-A2-02), and its `spec.source_ref` must equal `result.source_ref` (threaded from the draft by `validate_extraction`). One-shot acceptance (V6-P7-A2-03): a task that already produced a *different* output is refused; identical re-acceptance stays idempotent (PA4).
  1. **Admission gate:** only `ExtractionVerdict.ADMITTED` results have a write path — an `INVALID` verdict raises `ResearchClaimError` with the structured reasons (the validator already returned them; the repository refuses to persist them).
  2. **Integrity re-derivation (EC-V6 discipline):** every claim's `claim_id`/`content_hash` is re-derived with the *same* `claim_id_of`/`assumption_id_of` helpers; `schema_version` must equal `CLAIM_SCHEMA_VERSION`. Any mismatch raises `ResearchClaimIntegrityError` — fail-closed, nothing written. The repository never re-runs the validator's semantics (Model D).
  3. **Atomic single transaction:** rows (claims + assumptions + links) + §14 edges + supersession bookkeeping commit or roll back together — **no half-state** (IDR-013). A failure at any step rolls back everything.
  4. **Idempotency (PA4):** per-artifact `UNIQUE (project_id, content_hash)` — re-running the same batch inserts nothing new; existing rows are returned. A *changed* batch (same source, evolved claims) inserts only the genuinely new artifacts; a supersession with unchanged content fails loudly (the E9 rule: a new version changes the content, never silently drops).
  5. **Supersession:** `supersedes_id` must reference an existing, project-scoped, current-head row (a target that is itself already superseded is rejected — head-only). The target's assumption `status` is set `SUPERSEDED` **deterministically** in the same transaction (the one CT-R4 exception); `SUSPENDED` requires a human/Director `ResearchDecision` ref and is **deferred** (no decision machinery at P7 — documented, not implemented).
  6. **§14 provenance edges (same transaction):** `claim derived_from source-artifact`; `claim cites assumption` (premise citation, §10.2-style); `supersedes` edges for supersession. All three edge types are in the existing `provenance_edges` CHECK constraint — **no schema change for edges**. `extracted_by`/`produced_by` are recorded on the rows; the producing extraction task's own lifecycle events (TaskCreated/TaskStatusChanged) are the task-level audit.
  7. **No UPDATE/DELETE path exists at all** — immutability is structural.
- **Reads:** `get_claim`, `get_assumption`, `claims_for_project`, `assumptions_for_project`, `claims_depending_on(assumption_id)` (the link table query), `assumptions_of(claim_id)`, `head(claim_id)` — all deterministic, read-only.
- Errors: `ResearchClaimError` (governance), `ResearchClaimIntegrityError` (identity/integrity, subclass) — same taxonomy as the program repository.

## Decision 3 — Dereference resolver: what dereferences NOW vs. DEFERRED

§29.3 requires `dataset_ref` → DatasetManifest and `regime` → the versioned ICSS-v1 axis to dereference; dangling refs rejected deterministically. The schema reality (verified against `migrations.py`):

- **`dataset_ref` — ENFORCED at P7.** `dataset_manifests` exists (v4 §15/S12, `manifest_id`, `project_id`, `content_hash`, `immutable=1`). The write path constructs the real resolver: `(dimension='dataset_ref', value)` → true iff a manifest with `manifest_id = value` exists **in the intent's project** (cross-project dereference rejected — the §16.6/IDR-022 dereference discipline).
- **`regime` — DEFERRED (documented boundary, not a bypass).** The ICSS-v1 axis is ratified only as `regime_taxonomy_version` on spec/manifest (§11.1/H4, §27 item 6) — **no axis table exists in the schema**, and none is created by migration 4→5 (creating a fake axis registry would invent an authoritative carrier that v6 does not define). At P7 the resolver treats `regime` as form-checked (non-empty string, closed dimension) with a recorded `DEREFERENCE_DEFERRED` note on the row; enforcement activates with the axis store (P10, per §27 item 6) without schema change — the resolver is the extension point.
- **`methodology`** (§29.3 mentions → ExperimentSpec) — same deferral: no ExperimentSpec table at P7.

Rationale: the resolver is the single extension point for both dimensions; the substrate's `ContextResolver` protocol already makes this pluggable, and the golden fixtures (IDR-025) prove the rejection path with a stub. Enforcing `dataset_ref` now + documenting the `regime`/`methodology` boundary is honest P7 scope — not a silent weakening, and never a bypass: the closed dimension set and dereference contract are unchanged.

## Decision 4 — Audit trail: why this satisfies "no new event"

§29.1 forbids a new event type; the write path emits none. The audit is three-part and fully deterministic:

1. **The rows themselves** — immutable, content-addressed, `created_at` + `extracted_by`/`produced_by` recorded (the artifact-row-as-audit pattern already used by `scope_briefs`/`dataset_manifests`).
2. **The §14 `provenance_edges`** — `derived_from`/`cites`/`supersedes` written atomically, so "why does this claim exist" is a graph query, not prose.
3. **The producing task's existing events** — the extraction is task output; `TaskCreated`/`TaskStatusChanged` already journal the task lifecycle. The validator's admission verdict is recorded on the task output acceptance path (the S6 "validated before acceptance" rule), exactly as GR1's LitKG snapshot and S12's manifest registration are journaled without a dedicated event per artifact class.

If a future phase decides claims need a dedicated `ClaimExtractionAdmitted` audit event, that is a **five-stage amendment** (§29 preamble), not a P7 add-on — this record binds the zero-new-events rule now.

## Decision 5 — Who calls the repository (no new authority)

The write is **task-output acceptance**, not a gateway intent: the extraction task (C-tier) produces a schema'd output → `validate_extraction` decides admissibility (deterministic) → on ADMITTED, the task runtime calls `ClaimAssumptionRepository.record_extraction` inside the acceptance path. This is the same authority shape as GR1 (LitKG snapshot supersedes on re-extraction) and S12 (manifest registration): a deterministic validator + repository pair inside the existing controller/task-runtime acceptance, **no new intent kind, no new scheduler**. All *triggers* for later CONTRA passes still end at Reconcile (responsibility 8), PA5 re-entries, or `apply_intent` (§29.2 rule 8) — unchanged.

## Decision 6 — Deferred parts (explicit)

- `SUSPENDED` assumption transitions (need `ResearchDecision` refs; P11 when challenge machinery lands).
- `regime`/`methodology` dereference (P10 axis store / ExperimentSpec).
- Any `ClaimExtractionAdmitted` event (five-stage amendment only).
- Extraction-task pipeline itself (the task template, model tiering, budget) — P7 runtime integration, not this record.
- `ResearchClaim` → governed `Claim` citation wiring (§10.2, CT-R2) — the citation is by reference at P11; nothing here links to the ladder.

## Acceptance criteria for the future Part 3 (golden fixtures, §29.4)

1. Genuine ADMITTED extraction persists atomically (rows + links + edges); SQLite rows verifiable.
2. Forged `claim_id`/`content_hash` (hand-built, mismatching the canonical derivation) → `ResearchClaimIntegrityError`, **0 rows, 0 edges**.
3. INVALID verdict → `ResearchClaimError`, 0 rows (no partial batch).
4. Genuine duplicate batch → idempotent (same rows returned, no new rows, no duplicate edges).
5. Supersession: head-only; superseding with unchanged content fails loudly; target assumption flips to `SUPERSEDED` deterministically.
6. Dangling/cross-project `dataset_ref` → rejection at the write path (real resolver).
7. Failure injection at any step (row, link, edge, commit) → rollback, no half-state.
8. Never-evidence structural: persisted rows expose no ladder/validation surface; `status` CHECK allows only the advisory vocabulary.
9. No new event: event count/type set unchanged by a record_extraction call (only the producing task's existing events).
10. Queries: `claims_depending_on(assumption_id)` and `assumptions_of(claim_id)` return the validator-maintained links.
