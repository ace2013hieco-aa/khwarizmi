# IDR-021: P3 Intent Gateway (`apply_intent`) + ResearchTaskPlan + walking skeleton

**Status:** Decided + implemented + tested (P3 slice of v6 §28.5)
**Date:** 2026-08-13
**Decides for:** The v6 P3 slice that makes the ResearchProgram and the task graph operationally linked through the single authorized mutation path: the deterministic Intent Gateway, the program → task projection, and the walking skeleton that drives a compiled program through all three mandatory human gates.

## Context

v6 §28.5 phase discipline marked two P3 slices DEFERRED from the P2 session:

1. `PROPOSE_RESEARCH_PROGRAM` gateway wiring — `apply_intent` per-kind validator → `compile_from_payload` → `ResearchProgramCompiled` (AC-12: no compiler path bypasses the Intent Gateway).
2. Program → task admission via ordinary `INSERT_TASK`/GR7 (AC-05/10/12) plus the walking skeleton — "a fully stubbed project passes through all three mandatory gates (hypothesis, pre-compute, pre-live) with canned tool outputs" (v6 §24 P3 acceptance vehicle).

The v4 §8 intent vocabulary (`src/hermes/core/intents.py`) was already typed — `Intent`, `IntentKind`, `director_only()`, `IntentRejectedError` — with the docstring explicitly noting "the gateway itself (apply_intent) lands in P3 (deterministic runtime)". `src/hermes/research/gateway.py` was a 4-line placeholder. The Step-5 trust boundary (EC-V6-11..16) is the baseline this slice builds on: the repository remains the governance + identity/integrity authority; the gateway adds the admission authority on top.

## Decision

**Implement the P3 gateway, the task-plan projection, and the walking skeleton exactly within the §28.5 boundary. No authority moves.**

1. **`hermes/research/gateway.py` — `apply_intent(conn, intent, *, budget_check=None)`.** The single authoritative mutation path. Deterministic admission pipeline: kind → role → project → budget hook → per-kind validator → mutation (atomic with its own event inside the repository, IDR-013) → `IntentApplied` audit event. Any rejection appends `IntentRejected` and raises `GatewayRejection` (subclass of `IntentRejectedError`) with a stable code: `ROLE`, `UNKNOWN_KIND`, `NOT_WIRED`, `PROJECT_NOT_FOUND`, `MALFORMED_PAYLOAD`, `SCOPE_NOT_GOVERNED`, `NOT_COMPILED`, `STALE`, `BUDGET`, `DEPENDENCY`.
   - **Role enforcement (runtime, not just `director_only()` metadata):** `PROPOSE_RESEARCH_PROGRAM` admits only `DIRECTOR`; `ADMIT_TASK` admits only `DETERMINISTIC` (internal-only); `INSERT_TASK` admits the four agent profiles (`DIRECTOR`/`RESEARCHER`/`IMPLEMENTER`/`ADVERSARY`); unknown proposers rejected. §6 table tested: DIRECTOR → allowed; RESEARCHER/ADVERSARY/IMPLEMENTER/unknown → rejected.
   - **PROPOSE_RESEARCH_PROGRAM:** governance resolved by the repository (R-02 — the frozen brief's content hash, never trusted from the caller), supersession context via `superseded_program_ids` (E9 — head-only; a stale target is `STALE`), `compile_from_payload` (any non-COMPILED verdict is a `NOT_COMPILED` gate violation — compilation never equals approval, nothing persisted), `record` (idempotent, integrity-checked). Duplicate proposal → `duplicate=True`, no second event (PA4).
   - **INSERT_TASK / ADMIT_TASK:** strict closed-schema payload → `NodeContract` (unknown keys rejected, callers never set `status`), `TaskRepository.create` (cycle-checked, atomic, `TaskCreated`). Duplicate task_id → existing row returned (crash/retry idempotency, Attack N). Dependency violations → `DEPENDENCY` rejection — the graph stays a DAG.
   - **Budget:** a `budget_check` hook with a documented no-op default — the budget ledger is a deferred subsystem (no ledger exists in this tree); future budget slices plug in here. Not invented.
   - **Audit:** `IntentApplied`/`IntentRejected` events appended by the gateway (own transaction; the mutation + its own event stay atomic per IDR-013). A stale-project rejection audits with `project_id` NULL (events.project_id FK).
2. **`hermes/research/task_plan.py` — the program → task projection.** Pure, deterministic, content-addressed (AC-05/10/12). `build_task_plan(program)` emits gate tasks (`HUMAN_GATE` for the mandatory human gates, `GATE` for integrity gates) and evidence tasks (`AGENT_TASK`, profile RESEARCHER) with the v4 §9.1 DAG: hypothesis → pre_compute → integrity checks → evidence → pre_live. Task ids and idempotency keys derive from `program_id` + requirement (re-running cannot duplicate work). Every evidence task carries structural provenance links — `research_program:<id>`, `evidence_requirement:<claim_ref>`, `hypothesis:<claim_ref>`, `scope_brief:<scope_ref>` — so "why does task T exist" is recoverable from identifiers, never from LLM prose. `plan_to_payloads` produces valid INSERT_TASK payloads; `plan_to_nodes` produces `NodeContract`s. **No write surface** (structural test: no sqlite/repository/event imports in the module).
3. **Walking skeleton (tests).** `tests/test_walking_skeleton.py` drives a compiled program end-to-end: DIRECTOR proposes via the gateway → recorded → plan → all tasks admitted via `INSERT_TASK` → hypothesis/pre_compute/pre_live driven with canned human decisions → evidence tasks complete. Regression-testing the §24 acceptance vehicle. Rejection semantics: a failed hypothesis gate blocks evidence (F-10 dependency rule) and emits `GateFailed`.

## Rationale

1. **One mutation path, made real.** v4 §8's "there is no second write path" was a declared invariant; the gateway is its P3 runtime embodiment. The program cannot touch the task graph directly (H: plan has no write surface), the evaluator cannot dispatch (J: no write surface), and the graph cannot mutate (L: no graph component exists this phase).
2. **Authority separation preserved (Model D).** Validator = epistemic derivation; repository = governance + identity/integrity (R-02, EC-V6-11..16 intact — the gateway resolves governance via the repository and never re-derives identity); gateway = admission; task graph = operational. The gateway is NOT a second validator — it calls the compiler's own `compile_from_payload`.
3. **Gate semantics without inventing a gate subsystem.** The three mandatory gates are instantiated as `HUMAN_GATE` tasks in the plan; approval is a canned human decision in the skeleton (the general gate-runtime stays deferred). Integrity gates map to deterministic `GATE` nodes.
4. **Deferred, explicitly.** Not implemented (per §22 no-future-phase-leakage): Director proposal variant (P4), GR7 template binding (P6), program–spec binding (P8), graph integration (P7/P8), scheduler/ADMIT_TASK runtime, budget ledger, optimizer Part 2, Research Observatory, Research Debt, Uncertainty Budget, skill registry, graph database.

## Consequences

- **Implemented + tested:** the P3 slice above. Suite: **449 passed, 0 failed, exit 0** (384 post-Step-5 baseline + 61 P3 + 4 V6-FINAL-01/02 remediation regressions; `test_gateway.py` 30, `test_task_plan.py` 12, `test_walking_skeleton.py` 5, `test_v6_attacks.py` 18). See IDR-022 for the closure-gate remediation decision.
- **Attacks A–N (§21):** A/B unauthorized proposers rejected with nothing persisted; C forged COMPILED unreachable via the gateway (identity/status fields are unknown keys → rejected at compilation) and rejected at the write path (EC-V6-11..16) when forged directly; D–G forged content-hash/program-id/input-hash/schema-version/obligations all `ResearchProgramIntegrityError`, no row, no event; H no write surface in the plan; I evidence-status keys rejected at compilation (E8); J no dispatch surface in the evaluator; K gate-blocked candidate hard-excluded, never ranked (AC-03); L no graph mutation surface; M stale scope hash rejected at the write path (R-02), recompilation required; N duplicate proposal/task after retry is idempotent (PA4).
- **Authority boundaries:** the gateway CAN admit compiled programs and validated task nodes, enforce roles, reject, and audit; it CANNOT validate semantics itself (compiler's job), re-derive identity (repository's job), promote evidence, spend budget (hook only), or bypass any gate. Nothing in this slice is labeled RATIFIED — the external independent closure gate (v6 §27 item 43) remains the standing condition.
