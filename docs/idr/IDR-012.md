# IDR-012: Event Identity & Journal Semantics

**Status:** Decided (Phase 1)
**Date:** 2026-08-10
**Decides for:** How events are identified, ordered, and linked.

## Context

v3 §8.1: append-only event log with `event_id, type, payload_json, project_id,
task_id, created_at, causality_links`. Every state mutation emits exactly one
event. Events are never pruned at this scale.

## Decision

### Event identity
- `event_id INTEGER PRIMARY KEY AUTOINCREMENT` — monotonic, never reused,
  append-only. No UUID; the integer is the identity and the order.
- No API exposes UPDATE or DELETE on events. The repository's
  `append_event()` is the only write path.

### Causal linking
- `correlation_id TEXT NOT NULL` — UUID shared by all events produced in a
  single state transition (the transition + its event share one correlation_id).
- `caused_by TEXT` — the actor or system component that initiated the change
  (e.g., "controller", "operator", "scheduler", "system").
- `from_state` / `to_state` — the before/after state for transition events.
  Nullable for creation events (no prior state).

### Event ordering
- `event_id` (autoincrement) is the authoritative order. `created_at`
  provides human-readable timing but is not the sort key — `event_id` is.
- This avoids sub-microsecond ordering issues: two events in the same
  transaction get sequential `event_id` values, regardless of timestamp
  resolution.

### Payload
- `payload_json TEXT` — structured, event-type-specific data (JSON).
  Flexibility for different event types; not used for authoritative state
  (that's in the dedicated columns).

### Artifact linkage
- `artifact_ids_json TEXT` — JSON array of artifact_ids the event references
  (per v3 §14: "every event links to the artifact(s) that justified it").

### Reconstruction (Phase 1 req §20)
- Phase 1 uses **persisted current state + append-only events**, not pure
  event sourcing. The `projects` and `tasks` tables hold the current
  authoritative state; the `events` table is the audit trail.
- Reconstruction: `replay_events(project_id)` returns the event stream,
  verifying that the final event's `to_state` matches the persisted current
  state. A mismatch indicates corruption (tampering or a bug).
- There is no second source of truth. The event journal is auditable and
  consistent with authoritative state (Phase 1 req §20).
