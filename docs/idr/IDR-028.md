**Decides for:** How claim/assumption extractions become tasks in the existing task graph, how their outputs are accepted into the write path, and how the whole flow is journaled — **without adding any event type, intent kind, scheduler, or authority** (§29.1; §29.2 rule 8).

## Context

§29.3 says: "Extraction proposed by LLM tasks (C-tier), admissibility decided by a deterministic `ClaimAssumptionValidator` (the GR1/GR5/S6 validation pattern). No new event; per-artifact provenance + §14 edges." IDR-027 delivered the write path (`record_extraction`) but nothing calls it yet — this record designs the caller: the EXTRACT task and the task-output acceptance wiring that lands in `ClaimAssumptionRepository`.

## Governing constraints (re-derived against the ratified text)

1. **No new intents** (§29.1): the EXTRACT task is admitted through the **existing `INSERT_TASK`** gateway surface — the plan-proposed, gateway-validated task admission (§8; v4 §7 "nothing appears in the graph without passing the intent gateway"). No `EXTRACT` intent kind.
2. **No new scheduler** (§29.2 rule 8): all triggers end at the Reconcile loop (responsibility 5 — "submit appropriate intents through `apply_intent`"), PA5 scheduled re-entries, or `apply_intent`. The pipeline is *tasks*, not a daemon.
3. **No new events** (§29.1; IDR-026 Decision 4): the producing task's existing `TaskCreated`/`TaskStatusChanged` events + the immutable rows + §14 edges are the audit. No `ClaimExtractionAdmitted`.
4. **S6 validated-before-acceptance** (v2.1 §6, ds §16, preserved verbatim): "schema'd outputs validated before acceptance (malformed output = retryable task failure, never a partial write)" — this is exactly where `validate_extraction` sits.
5. **Model tiers (M1)** — C (cheap) is the extraction tier ("Researcher bookkeeping", small context budget); `model_ref` recorded on the artifacts, never authoritative lineage.
6. **Manual-proof-first** (§29.2 rule 7): the acceptance wiring ships golden fixtures before any scheduled execution.
7. **Never-evidence** (§29.2 rule 1; PA2/GR3): extraction output is advisory; admissibility ≠ evidence; `record_extraction` forces ACTIVE; nothing here touches the ladder.

## Decision 1 — The EXTRACT task template

An EXTRACT task is an ordinary **`AGENT_TASK`** node admitted via `INSERT_TASK`:

```
INSERT_TASK {
  task_id:        "extract_<sha256(source_ref+scope+template_version)[:24]>",
  task_type:      "AGENT_TASK",
  profile:        "RESEARCHER",            # C-tier execution profile
  idempotency_key: sha256("extract:" + source_ref + ":" + scope + ":v1"),
  spec: {
    source_ref:   "dataset_manifest:<id>" | "<artifact_type>:<ref>",   # dereferenceable at admission (IDR-027 F02)
    scope:        "claims+assumptions",     # what to extract (closed vocabulary: claims / assumptions / both)
    template_version: "1",
    extracted_by_expected: "model_ref:<C-tier>",   # advisory; recorded, never trusted
  },
  dependencies: [ <source acquisition / validation tasks if any> ],  # F-10 readiness
  cost_class:   "small",                    # C-tier context budget (§17 M1)
  provenance:   { "source_ref": ... },      # ordinary task provenance (V6-FINAL-02 discipline)
}
```

- **Identity/content-addressing:** task_id derives from source + scope + template version — re-extraction of the same source with the same template is the same task (PA4 idempotency at the task level, before any claim exists).
- **Gate structure:** no new gate; the EXTRACT task depends on the source artifact being available (its acquisition/validation task SUCCEEDED, per F-10). A source that is a `dataset_manifest` requires the manifest's registration task (or the manifest existing in `dataset_manifests`).
- **Who proposes:** the Reconcile loop (responsibility 3 gap detection → responsibility 5 intent submission) or the Director's gap proposal (`INSERT_TASK` is LLM-proposable by the four profiles; the loop submits it DETERMINISTIC-style through the same `apply_intent`). Both are existing paths — no new proposer role.

## Decision 2 — Task-output acceptance wiring (the deterministic gate)

The EXTRACT task's output contract is the **`ExtractionDraft` schema** (claims + assumptions + source_ref + extracted_by + schema_version — `claims.py`). Acceptance is the S6 validated-before-acceptance path:

```
EXTRACT task RUNNING
    ↓  C-tier model produces ExtractionDraft JSON
task-output acceptance:
    ├── validate_extraction(draft)                     # ClaimAssumptionValidator — deterministic
    │       ├── ADMITTED  → record_extraction(project_id, result,       # IDR-027 write path
    │       │              extracted_by=<model_ref>, reason="extract task <id>")
    │       │              → task → SUCCEEDED (existing TaskStatusChanged)
    │       └── INVALID   → retryable task failure (existing retry path, §19/PA2 bounds)
    │                      → no partial write (S6: malformed output never becomes a partial record)
```

- **Where it lives:** inside the controller's task-output acceptance (the same place any schema'd output is validated before acceptance — v2.1 §6, ds §16). The validator is the deterministic gate; `record_extraction` is the write; the task runtime never writes rows itself.
- **Failure semantics (IDR-026/027 preserved):** INVALID verdict → task FAILED/RETRYING, 0 rows, 0 links, 0 edges (the write path's admission gate + integrity boundary are the second and third lines of defense). A crash mid-acceptance → task retry re-validates + re-records idempotently (PA4; `UNIQUE(project_id, content_hash)`), never duplicates.
- **Extraction is not approval:** an ADMITTED extraction is the advisory substrate only — it changes no evidence, passes no gate, and `record_extraction` forces ACTIVE status (V6-P7-F01). The pipeline can never promote.

## Decision 3 — Journaling without new events

The full audit trail for one extraction, all existing mechanisms:

1. **`TaskCreated`** — the EXTRACT task entering the graph (gateway `INSERT_TASK` admission event, §8).
2. **`TaskStatusChanged`** — RUNNING → SUCCEEDED/FAILED, carrying the task lifecycle (existing event; the acceptance verdict is recorded on the output acceptance path, the S6 pattern — as GR1's LitKG snapshot and S12's manifest registration are journaled without a dedicated event).
3. **The immutable rows + §14 edges** — `research_claims`/`research_assumptions`/`claim_assumption_links` + `derived_from`/`cites`/`supersedes` edges (IDR-026 Decision 4).
4. **`model_ref` on the rows** (`extracted_by`) — the C-tier contribution is tagged, never authoritative lineage (§29.3).

No new event type, no `ClaimExtractionAdmitted`, no change to the §8.1 catalog or the persistence-boundary allowlist. If a future phase decides a dedicated event is needed, that is a **five-stage amendment**, not a P7 add-on (IDR-026 Decision 4).

## Decision 4 — Trigger model (no new scheduler)

- **Event-triggered:** a new `DatasetManifest` registered / source artifact validated → Reconcile responsibility 3 sees the gap ("this source has no extraction yet") → proposes the EXTRACT task.
- **Reconciliation-driven:** a claim-relevant artifact exists without extractable claims in the corpus → the same gap mechanism.
- **Operator-triggered:** manual "extract from source X" through the ordinary intent path (`INSERT_TASK` proposed by DIRECTOR).
- **Not now:** no periodic corpus sweep, no daemon, no watcher (the CONTRA scheduler was rejected — CT-03). A future staleness/re-extraction scan is a PA5 scheduled re-entry, designed when re-extraction policy exists (P11+).

## Decision 5 — Boundaries and deferrals (explicit)

- **DESIGNED now, not implemented:** the EXTRACT task template, the acceptance-wiring contract, the journaling story.
- **DEFERRED (with the pipeline's own later phase):** the actual C-tier model call and `ModelClient` task template (P7 runtime integration); tool allowlist for source readers; budget-ledger charging of extraction tasks (the deferred budget hook, §28.5); re-extraction/staleness policy (PA5 scan, P11+); contradiction contextualization and steelman (P11 — they consume the substrate this pipeline feeds).
- **REJECTED:** any EXTRACT intent kind; any extraction scheduler/daemon; any LLM-admissible write path (the validator + repository remain the only write path — the V6-P7 audit posture is preserved).

## Acceptance criteria for the future Part 3 (golden fixtures)

1. An EXTRACT task admitted via ordinary `INSERT_TASK` is an `AGENT_TASK` with the C-tier profile and the content-derived idempotency key.
2. A well-formed `ExtractionDraft` output → `validate_extraction` ADMITTED → `record_extraction` called → rows + links + edges exist; task transitions SUCCEEDED.
3. A malformed output → INVALID → task FAILED/RETRYING, **0 rows, 0 links, 0 edges** (no partial write).
4. Re-running the same extraction after a crash → idempotent (task-level and artifact-level; no duplicate rows, no duplicate edges).
5. The acceptance wiring emits **no new event type** (event catalog + allowlist unchanged; only existing TaskCreated/TaskStatusChanged/IntentApplied).
6. The acceptance wiring can never promote evidence, pass a gate, or set a status other than ACTIVE.
7. An EXTRACT task for a source whose dereference fails (missing `dataset_manifest`) is rejected at admission (the IDR-027 F02 discipline, enforced earlier).
8. The pipeline's own `model_ref` is recorded on rows and is never authoritative lineage.

## Implementation (IDR-028 → code)

**`src/hermes/research/extraction.py`:**
- `build_extract_task_payload(source_ref, scope, ...)` — the deterministic EXTRACT template: `AGENT_TASK`, RESEARCHER/C-tier, `extract_<sha256>[:24]` task id + content-derived idempotency key, closed payload shape (the gateway's own key set), `cost_class=small`. Unknown scope / non-`artifact_type:ref` source rejected by the template.
- `extraction_draft_from_mapping` — strict JSON → `ExtractionDraft` (fail-closed on unknown keys, EC-F01 style; type-checked context tags and ref lists).
- `accept_extraction_output(conn, project_id, task_id, draft, *, extracted_by, reason)` — the S6 wiring, **bound to the producing task** (V6-P7-E03 remediation): the `task_id` must exist, be RUNNING, be an EXTRACT task, and its `spec.source_ref` must equal the draft's `source_ref` (else `ExtractionNotBoundToTask`, no write). Then `validate_extraction` decides admissibility; ADMITTED → `record_extraction`; INVALID → `ExtractionOutputRejected` (retryable, no partial write).

**`src/hermes/research/gateway.py` — `_validate_extract_source`:** criterion 7 enforced at admission — an EXTRACT task whose `spec.source_ref` fails project-scoped dereference (e.g. missing `dataset_manifest`) is rejected with `PROVENANCE`/`MALFORMED_PAYLOAD` before any task row exists. This closes a real gap the fixtures exposed (the gateway previously admitted EXTRACT tasks against nonexistent sources). The check runs only for `spec.template == "extract"`; ordinary INSERT_TASK semantics untouched.

**`tests/test_extraction_pipeline.py` — 16 golden fixtures** mapping the 8 acceptance criteria: template shape + determinism; ordinary-gateway admission as AGENT_TASK/C-tier; well-formed output → rows+links+edges+SUCCEEDED; malformed output → `ExtractionOutputRejected` + 0 rows + task left non-terminal; schema-drift unknown key fails closed; crash/rerun idempotent at task and artifact level; event catalog + allowlist unchanged (delta = exactly the known pre-existing F-15 drift); no promotion/gate/ladder surface; missing-manifest rejection at admission AND at output acceptance; `extracted_by`/`reason` recorded as row provenance, never lineage.
