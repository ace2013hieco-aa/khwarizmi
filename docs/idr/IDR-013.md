# IDR-013: Transaction/Event Atomicity & Failure Semantics

**Status:** Decided (Phase 1)
**Date:** 2026-08-10
**Decides for:** How state transitions and events are committed atomically.

## Context

Phase 1 req §10: "A state transition must NOT be persisted successfully while
its event fails to persist." Use a single SQLite transaction:
`BEGIN → validate → update state → append event → COMMIT`. If anything fails:
`ROLLBACK`. v3 §8.1: "every mutation is command → validate → apply → event in
one transaction."

## Decision

### Single-transaction transition
Every authoritative state mutation follows this pattern:

```python
with conn:  # BEGIN ... COMMIT (or ROLLBACK on exception)
    validate_transition(...)  # raises TransitionError if illegal
    conn.execute("UPDATE ... SET state = ? WHERE ...", (new_state,))
    conn.execute("INSERT INTO events ... VALUES (...)", (...))
    # COMMIT on success, ROLLBACK on exception
```

`sqlite3.Connection` as a context manager automatically commits on clean exit
and rolls back on any exception — this is the atomicity guarantee.

### Failure semantics
- If `validate_transition` raises → no UPDATE, no INSERT, ROLLBACK.
- If the UPDATE fails → no INSERT, ROLLBACK.
- If the INSERT (event) fails → ROLLBACK (the UPDATE is undone).
- The caller sees an exception; the state is unchanged; no partial event.

### Artifact write + DB commit (Phase 1 req §22)
- Artifact content is written to the filesystem *first* (before the DB
  transaction).
- The DB transaction then records the artifact metadata + appends an event.
- If the DB commit fails: the artifact content is orphaned (no DB record).
  Orphaned content is safe — it cannot be cited or referenced. A cleanup
  pass (future) removes it.
- If the filesystem write fails: no DB transaction starts; no false claim
  of artifact existence.
- The store never falsely claims an artifact is authoritative.

### Testing (Phase 1 req §22)
- Failure injection: mock the event INSERT to raise → assert state unchanged
  and no event in the journal.
- Failure injection: artifact write succeeds, DB commit fails → assert no
  artifact metadata record exists.
- Both tested explicitly in the test suite.

## Addendum — AUDIT-TXN (GAP-1 D12 / P2-7): same-transaction audit append

**Date:** 2026-10-23. **Base:** `76962af`. **Ruling:** D12-A.
**Home:** this IDR. No other IDR owns it — IDR-040/041 decide what a decision
record contains, `TAMPER-EVIDENT-JOURNAL` owns the chain preimage, and neither
decides transaction ownership. This is the transition/event atomicity question
IDR-013 was written for.

**Defect.** `apply_intent` (`gateway.py:4570`) dispatches to a validator that
calls a write path owning its own `BEGIN … COMMIT`. Only after that commit
returns does `apply_intent` append `IntentApplied` (`gateway.py:4725`) via
`_append_audit_event` (`gateway.py:4729`) → `EventRepository.append_transactional`
(`repositories.py:838`), a second `BEGIN … COMMIT`. A crash between the two
commits leaves a durable mutation with no audit row.

### A1.2 Mechanism

**Chosen: thread the audit event into each owner's existing commit, as explicit
data.**

1. `_append_audit_event` becomes a **pure builder**: same name (it stays one of
   the two permitted `origin_*` readers, pinned by
   `test_idr045_plan_admission_and_provenance.py`; the other is
   `_require_provenance_bounds`), same payload and clamping logic, returns an
   immutable `AuditRecord` (`event_type`, `project_id`, `correlation_id`,
   `caused_by`, `reason`, `payload`) instead of writing.
   `AuditRecord` is defined in `hermes/persistence/repositories.py` beside
   `_append_event_to_db`, so the import direction stays gateway→persistence and
   no persistence→research import is added.
2. `apply_intent` builds the applied record once, immediately before dispatch,
   validates it with `validate_event` (the same 4 KiB / secret / event-type gate
   the writer applies), and passes it to the dispatched validator as `audit=`. An
   `EventValidationError` from that gate is mapped to
   `_reject(kind, MALFORMED_PAYLOAD, …)` so the refusal is structured and
   journalled like every other pre-write refusal. This makes the 4 KiB cap
   literally pre-write: today it fires after the mutation commit and strands the
   mutation; under fusion it would unwind it, so validating the record first is
   both cheaper and stricter.
3. **Gateway-owned owners** (`_decision_append_transactional`,
   `_validate_retract_source`, `_validate_curate_knowledge`,
   `_validate_record_contradiction`, `_validate_contradiction_resolution`) call
   `_append_event_to_db(conn, clock, audit…)` immediately **before their
   existing `COMMIT`**, on the branch that commits.
4. **Persistence-owned owners** (`ResearchProgramRepository.record`,
   `EventRepository.append_transactional`,
   `FailureClassificationRepository.record`,
   `OperatorCredentialRepository._apply_credential_mutation`,
   `TaskRepository.create`) take a keyword-only `audit: AuditRecord | None` and
   do the same before their existing `COMMIT`. `revoke`/`rotate` forward it.
5. `apply_intent` writes the audit row itself, through
   `_write_audit_event` → `EventRepository.append_transactional` (its own
   transaction), **only when the call wrote no mutation**: `result.duplicate` is
   true, or the call was rejected. The fused path never calls
   `append_transactional`, so the FK ROLLBACK-retry cannot run inside a
   mutation transaction.

Per-owner append rule:

| owner | appends the handed record on | who appends when it wrote nothing |
|---|---|---|
| `_decision_append_transactional` | the `appended` branch, before `COMMIT:1046` | `apply_intent` (duplicate) |
| `_validate_retract_source` | success, before `COMMIT:2129` | `apply_intent` (duplicate `:2051`) |
| `_validate_curate_knowledge` | success, before `COMMIT:2883` | `apply_intent` (duplicate `:2758`) |
| `_validate_record_contradiction` | success, before `COMMIT:3258` | `apply_intent` (duplicate `:3135`) |
| `_validate_contradiction_resolution` | success, before `COMMIT:3479` | `apply_intent` (duplicate `:3420`) |
| `ResearchProgramRepository.record` | whichever branch it takes: new write before `COMMIT:1877`, in-transaction duplicate before `COMMIT:1775` | `apply_intent`, when the validator passed no record (pre-read said duplicate) |
| `FailureClassificationRepository.record` | `decision == "NEW"`, before `COMMIT:321` | `apply_intent` (`REUSED`) |
| `OperatorCredentialRepository._apply_credential_mutation` | non-duplicate mutation, before `COMMIT:1346` | `apply_intent` (revoke replay) |
| `TaskRepository.create` | always (called only for a new task), before `COMMIT:492` | `apply_intent` (task duplicate, returned at `gateway.py:4519`) |
| `EventRepository.append_transactional` | always, before `COMMIT:875` | `apply_intent` (proposal duplicate, returned at `gateway.py:968`) |

The program row is deliberate: its duplicate decision is a pre-read *outside*
the transaction (`gateway.py:565`, `:812`), so the validator passes the record
only when the pre-read says "new"; the repository appends the handed record on
whichever branch it lands. That closes the pre-read/write race without a second
signal. For the other persistence owners the write/no-write decision is made
inside the transaction and returned, so the validator's `duplicate` flag is
authoritative and exactly one side appends.

**Rejected alternatives.**

- *Wrap the dispatch in a transaction the owners join by detecting an open
  transaction.* SQLite rejects a nested `BEGIN`, so every owner's control flow
  becomes conditional — 10 owners and 21 `BEGIN`/`COMMIT` statements touched for
  no census benefit. Worse, five owners signal duplicate/conflict by six
  `ROLLBACK`-and-return statements (`gateway.py:1032`, `:1038`, `:2051`,
  `:2758`, `:3135`, `:3420`); a wrapper cannot tell "committed" from "aborted
  and returned duplicate" without the same outcome signal used here. And "is a
  transaction open" is connection state — the hidden state the charter rejects.
- *Connection attribute, thread-local, or module global carrying the pending
  audit event.* Rejected outright: invisible at the call site and able to leak
  across requests on a reused connection. `AuditRecord` is a parameter; it lives
  on the stack of one call and cannot outlive it.
- *Deferred outbox flushed at commit.* Rejected: stdlib `sqlite3` exposes no
  commit hook, and a separate table plus flusher reintroduces a crash window
  between flush and apply — the same defect one layer out.
- *Hoist the audit append into the mutation's own event payload.* Rejected: it
  changes the mutation event's shape and its content hash surface, and it
  destroys the one-row-per-intent audit contract the tests pin.

### A1.3 Invariants

1. **No durable mutation without its audit row.** The audit INSERT is in the
   same transaction as the mutation INSERT. Any failure before `COMMIT` —
   including the audit INSERT itself — takes the owner's existing `except` path
   and rolls the mutation back. The crash window between the two commits no
   longer exists because there are no two commits.
2. **No `IntentApplied` without the mutation.** The fused row can only be
   written on a branch that has already written the mutation in that
   transaction; a rollback removes both. On the duplicate path the call writes
   nothing and its audit row stands alone — but the mutation it reports is
   durable from the earlier admission, which fused its own audit row, so the
   record never claims a mutation that does not exist. Rejections write
   `IntentRejected`, never `IntentApplied`.
3. **Refusal-as-data is unchanged.** A rejected intent still lands exactly one
   `IntentRejected` row, byte-identical to today: same event type, same
   `reason="intent rejected"`, same payload and clamping
   (`gateway.py:4754-4806`); the `GatewayRejection` code and reason still travel
   verbatim on the exception. **A rejection's audit row stays its own
   transaction.** That is not a regression: a rejection produces no mutation, so
   there is nothing to fuse and nothing that can be stranded. Its own
   transaction is also what keeps the `retry_without_project` FK fallback
   available.
   **FK fallback hazard.** `append_transactional` resolves a stale-project FK
   failure by `ROLLBACK`-then-`BEGIN` (`repositories.py:868-869`). Inside a
   fused transaction that ROLLBACK would undo the mutation. The fused path
   therefore never calls `append_transactional` and never passes
   `retry_without_project`; it calls `_append_event_to_db` directly, where no
   retry exists. This is safe because the project column is known-valid at that
   point: `_require_project` ran before dispatch (`gateway.py:4630`), the
   mutation row written in the same transaction carries `intent.project_id` and
   satisfied the FK, and the transaction holds the write lock so the project row
   cannot be deleted before the audit INSERT. If the audit INSERT nevertheless
   fails, the transaction rolls back — no mutation, no audit row, and
   `apply_intent` journals a rejection in its own transaction. A
   `ROLLBACK`-then-retry inside a fused transaction is unreachable by
   construction.

### A1.5 TAMPER-2 interaction

`_append_event_to_db` (`repositories.py:119`) is the single chain writer: it
reserves `event_id` (`_next_event_id`, `:102`), reads the tip (`journal_tip`,
`:156`), computes `prev_hash`/`chain_hash`, and INSERTs — all in the caller's
already-open transaction, by contract (`:140-148`, addendum A7.2). Fusion makes
that caller's transaction the mutation's transaction, so **the tip read stays
inside the transaction that writes the mutation**. The audit row is chained
directly onto the mutation's own event, with no interleaving possible under
SQLite's single-writer rule — strictly stronger than today, where another
writer can land an event between the mutation commit and the audit commit. No
chain semantics change: same preimage, same field order, same verification.
**Nothing bypasses `_append_event_to_db`**: the fused path calls it directly,
the non-fused path calls it through `append_transactional`, and the diff adds no
raw `INSERT INTO events`. A fused audit row that skipped the chain writer would
be a defect; it cannot occur because the append is a call to that function.

### A1.6 Falsifiers

The implementing phase must ship `tests/test_audit_txn_atomicity.py`:

1. `test_fault_between_mutation_and_commit_leaves_neither_row` — patch
   `hermes.persistence.repositories._append_event_to_db` to raise only for
   `event_type == "IntentApplied"`, then apply one persistence-owned intent
   (ADMIT_TASK) and one gateway-owned intent (CURATE_KNOWLEDGE). Assert the
   mutation row and its own event are absent, `IntentApplied` is absent, and
   exactly one `IntentRejected` exists. This closes the crash window in the
   forward direction.
2. `test_fault_after_commit_leaves_both_rows` — patch the owner to raise after
   its `COMMIT` returns (e.g. `TaskRepository.create` calls the original then
   raises). Assert the mutation row and the `IntentApplied` row both exist. This
   closes it in the backward direction. (The post-commit failure also lands an
   `IntentRejected` through the existing `except Exception` arm, as it does
   today; the mutation is durable, so the `IntentApplied` is not a false claim.)
3. `test_rejection_journals_exact_code` — a role, project, and payload refusal
   each land exactly one `IntentRejected` with the unchanged payload, while the
   raised `GatewayRejection.code` is exact.
4. `test_stale_project_rejection_falls_back_to_null_project` — a stale-project
   rejection writes `IntentRejected.project_id IS NULL`, keeps the project id in
   the payload, and touches no mutation table.
5. `test_4kib_cap_refuses_before_any_write` — an applied intent whose audit
   payload would exceed 4096 bytes is refused before dispatch (`validate_event`
   in `apply_intent`, mapped to `MALFORMED_PAYLOAD`), leaving no mutation row and
   exactly one `IntentRejected`; and a direct over-cap `_append_event_to_db`
   inside a fused transaction rolls the mutation back (no row survives).
6. `test_every_applied_intent_has_one_adjacent_audit_row` — for one intent of
   each of the 13 branches: exactly one `IntentApplied`, and its `prev_hash`
   equals the mutation event's `chain_hash` (same-transaction adjacency).
7. `test_duplicate_replay_lands_one_applied_row_and_no_write` — replay of each
   duplicate path: one `IntentApplied`, no new mutation, state unchanged.
8. `test_chain_verifies_after_fused_apply` — `verify_journal` reports OK after
   a fused apply; no `CHAIN_UNCHAINED_ROW`.
