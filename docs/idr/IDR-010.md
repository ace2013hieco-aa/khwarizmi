# IDR-010: Migration Mechanism — Forward-Only, Versioned

**Status:** Decided (Phase 1)
**Date:** 2026-08-10
**Decides for:** How the database schema evolves over time.

## Context

v3 §16.4: schema versioning. Phase 1 req §14: detect schema ==, <, >
supported; handle each explicitly. Never silently operate against an
unknown future schema.

## Decision

**Forward-only migration with a `schema_version` table.**

### Schema version tracking
- A `schema_version` table holds the current applied version (single row).
- On startup: read the version, compare against `SUPPORTED_VERSION`.
- `database_schema == supported` → proceed normally.
- `database_schema < supported` → run pending migrations in order.
- `database_schema > supported` → refuse to start, raise
  `SchemaVersionError`. Never silently operate against a future schema.

### Migration registry
- Migrations are Python functions registered in a list, indexed by version
  number: `MIGRATIONS = [migrate_0_to_1, migrate_1_to_2, ...]`.
- Each migration takes a `sqlite3.Connection` and runs DDL within a
  transaction.
- Migrations are forward-only — no down/rollback migration. If a rollback
  is ever needed, it is a manual operation against a backup snapshot.

### Phase 1
- `SUPPORTED_VERSION = 1`.
- `migrate_0_to_1` creates all v1 tables (IDR-007) from a clean database.
- There is no "version 0" — a database with no `schema_version` table
  is treated as version 0 and migrated to 1.

### Testing
- Test migration from a clean (nonexistent) database → version 1.
- Test migration from version 0 → version 1 (existing empty DB).
- Future: test from version N → version N+1 as migrations are added.
