# IDR-027: CONTRA P7 write path — implementation (migration 4→5, ClaimAssumptionRepository, dataset_ref resolver, golden fixtures)

**Status:** Implemented + Tested (25 golden fixtures; authoritative suite 500 passed, 0 failed). The extraction-task pipeline and `regime`/`methodology` dereference remain **DEFERRED** exactly as IDR-026 Decision 6 specifies — this record implements the designed write path, nothing more.
**Date:** 2026-08-13
**Decides for:** The Part 3 implementation of the IDR-026 write path — the persistence layer for the advisory `ResearchClaim`/`ResearchAssumption` artifacts, per the manual-proof-first rule and the zero-new-authority constraint.

## Context

IDR-026 designed the P7 write path: migration 4→5 (three typed tables), `ClaimAssumptionRepository` (admission gate, integrity re-derivation, atomic single transaction, per-artifact idempotency, head-only supersession, §14 edges, no events), and the real dereference resolver (`dataset_ref` enforced, `regime`/`methodology` deferred). This record lands that design against real SQLite with the 10 acceptance criteria as golden fixtures.

## What was implemented

**`src/hermes/persistence/migrations.py` — `_migrate_4_to_5` (version 5, `SUPPORTED_VERSION = 5`):**
- `research_claims` — content-derived `claim_id`, `UNIQUE (project_id, content_hash)`, head-only `supersedes_id` with self-supersede CHECK, no UPDATE/DELETE path.
- `research_assumptions` — same identity/idempotency pattern plus `status CHECK (ACTIVE/SUSPENDED/SUPERSEDED)` (advisory lifecycle only).
- `claim_assumption_links` — the normalized, FK-enforced relation behind `assumption_ids[]`/`dependent_claim_ids[]`.
- Indexes: project, content_hash, supersedes_id per table; assumption-side link index. Registered in `_MIGRATIONS`.

**`src/hermes/persistence/repositories.py` — `ClaimAssumptionRepository` (governance + integrity authority):**
- `record_extraction(project_id, result, *, extracted_by, reason)` — the write path: (1) only `ADMITTED` results persist (structured reasons otherwise); (2) EC-V6 integrity boundary — every `claim_id`/`content_hash`/`assumption_id` re-derived with the same pure helpers (`claim_id_of`/`assumption_id_of`), `schema_version` checked, batch-internal assumption links enforced — any mismatch raises `ResearchClaimIntegrityError`, fail-closed, 0 rows/links/edges; (3) the real dereference resolver (`_make_resolver`); (4) `BEGIN IMMEDIATE` single transaction: assumptions → claims → links + §14 edges (`derived_from`, `cites`, `supersedes`) → deterministic `SUPERSEDED` flip for superseded assumption targets (CT-R4's one deterministic case); (5) per-artifact idempotency (PA4) with the E9 unchanged-content rule failing loudly; (6) **no event emitted** (IDR-026 Decision 4 — audit is the immutable rows + §14 edges + the producing task's existing events).
- Read side: `get_claim`, `get_assumption`, `claims_for_project`, `assumptions_for_project`, `claims_depending_on(assumption_id)`, `assumptions_of(claim_id)`, `head(claim_id)` — deterministic, no update/delete surface.
- Errors: `ResearchClaimError` (governance), `ResearchClaimIntegrityError` (identity/integrity subclass).

**Resolver (`_make_resolver`):** `dataset_ref` → must resolve to a `dataset_manifests` row in the intent's project (cross-project dereference rejected — the §16.6/IDR-022 discipline); `regime`/`methodology` → form-checked only, recorded as deferred dimensions (IDR-026 Decision 3: no axis table exists at P7, and migration 4→5 invents none).

**`tests/test_claims_write_path.py` — 25 golden fixtures** mapping the IDR-026 acceptance criteria 1–10 one-to-one, plus the migration 4→5 upgrade path and FK enforcement:
1. genuine admission persists atomically (rows + links + §14 edges verifiable in SQLite);
2. forged `claim_id` / `content_hash` / `schema_version` / out-of-batch assumption link → `ResearchClaimIntegrityError`, 0 rows, 0 edges;
3. INVALID verdict and empty ADMITTED → `ResearchClaimError`, no partial batch;
4. genuine duplicate → idempotent (no new rows/links/edges, first-admission provenance retained); evolved batch inserts only new artifacts;
5. head-only supersession with deterministic `SUPERSEDED` target flip + supersedes edge; unchanged-content supersession fails loudly (substrate self-supersession); missing target rejected;
6. dangling `dataset_ref` and cross-project `dataset_ref` → write-path rejection; valid ref admitted;
7. failure injection on link insert and on edge insert → rollback, no half-state, next attempt succeeds;
8. never-evidence structural: no ladder/validation/evidence columns, `status` CHECK rejects non-advisory values, no promote/advance/update/delete surface;
9. `record_extraction` emits **no events** (event count and type set unchanged);
10. link queries return the maintained links; `head` follows the supersession chain.

## Decisions

- **No new events, intents, or authorities** — verified by test 9 (event set unchanged) and the repository's lack of any `_append_event` call.
- **Identity discipline carried to the write path:** the repository re-derives identity with the same helpers the validator uses — one canonical derivation, never two (the EC-V6-20 discipline extended to claims).
- **Supersession semantics:** the target must exist, be project-scoped, be the current head, and differ in content; the target assumption flips to `SUPERSEDED` deterministically in the same transaction. `SUSPENDED` remains human/Director-driven (deferred — no decision machinery at P7).
- **Status vocabulary is advisory-only:** `status` CHECK is the three-value lifecycle; the never-evidence rule is enforced structurally (test 8).

## Relation to the ratified baseline

- No ratified §28 text, no §27 item below 47, no ladder/§19/GR3/§21 rule modified.

## Audit-2 remediation — V6-P7-A2-01..03 (producing-task binding in the write path)

The post-E03 hostile audit found the task binding lived only in the pipeline layer: `record_extraction` could persist claims with no task anywhere, and the persisted rows carried no task reference. Closed here:

- **Migration 5→6 (`_migrate_5_to_6`, `SUPPORTED_VERSION = 6`):** `producing_task_id TEXT REFERENCES tasks(task_id)` via `ADD COLUMN` (nullable, forward-only) on `research_claims`/`research_assumptions` + per-table indexes. The schema is now task-bound.
- **`record_extraction` requires `producing_task_id`** and verifies it INSIDE the `BEGIN IMMEDIATE` write transaction (atomic with the write, closing the A2-02 TOCTOU window): task exists, belongs to `project_id`, is an EXTRACT task (normalized marker, same check as the gateway), is RUNNING, and its `spec.source_ref` equals `result.source_ref` (`ExtractionResult` now threads the draft's `source_ref` — substrate change in `claims.py`).
- **One-shot acceptance (A2-03):** a task that already produced a *different* output is refused (`ExtractionTaskBindingError`); identical re-acceptance stays idempotent (PA4).
- **8 new regression fixtures** (`test_a2_01_*`/`test_a2_02_*`/`test_a2_03_*`/`test_a2_05_*`) proving the closed surfaces; all write-path fixtures updated to the bound signature (each admission now carries its producing RUNNING EXTRACT task). Re-verified by the independent audit-2 probe script: 5/5 probes, 0 flagged. Authoritative suite 539 passed, 0 failed.
- The write path now sits at **IMPLEMENTED + TESTED** (IDR-026 DESIGNED → this record). Still no authority conferred, no runtime behavior changed outside the new repository: nothing calls `record_extraction` yet — that is the extraction-task pipeline, explicitly deferred.

## Independent audit + remediation (V6-P7-F01..F04)

An independent hostile audit (`~/.ix/reports/p7_audit/p7_write_path_attack.py`, 11 probes + follow-ups) attacked the write path with hand-built forgeries, failure injection, and a SQL-injected two-node supersession cycle. The core defenses held (identity forgeries fail closed, cross-project/non-head supersession rejected, `head()` cycle guard works, failure at the last transaction step rolls back, duplicate batches idempotent, no raw IntegrityError). Four findings were remediated in this record:

- **V6-P7-F01 (P2) — status forged at admission:** `record_extraction` now forces `status='ACTIVE'`; SUPERSEDED is the repository's own deterministic flip only (CT-R4).
- **V6-P7-F02 (P2) — dangling `source_ref`:** the write path now dereferences `source_ref`/`supporting_artifact_refs` against existing carriers (`dataset_manifest:` project-scoped) via `_dereference_artifact_ref`; deferred artifact types stay form-checked (documented extension point).
- **V6-P7-F03 (P3) — raw FK error:** explicit project-existence check raises `ResearchClaimError` before the transaction.
- **V6-P7-F04 (P3) — dead `reason`:** `reason` is now persisted on both tables (migration 4→5 gains the columns).

Regression tests: `test_f01_…`..`test_f04_…` in `tests/test_claims_write_path.py` (6 new; 25 → 31). Audit report: `~/.ix/reports/p7_audit/V6-P7-write-path-audit-report.md`.
