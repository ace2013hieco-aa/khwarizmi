# IDR-016: `scheduler_lock` Disposition — Dormant-by-Design for P1

**Status:** Decided (Phase 1)
**Date:** 2026-08-11
**Decides for:** Whether the `scheduler_lock` advisory lock is wired into the repository write path during Phase 1.

## Context

The hostile re-verification report (§C.1) found that `acquire_writer_lock`/`release_writer_lock` in `database.py` have zero production callers — no code in `src/hermes/` outside `database.py` and test files calls them. The repository mutation methods rely solely on SQLite's `BEGIN IMMEDIATE` transaction exclusivity for mutual exclusion. The lock primitive exists and is tested (P1's "stale-lock rejection" validation criterion), but it is not integrated into the write path.

### Relevant v4 text

**§8 (line 356) — Single-writer discipline:**
> "One controller instance per project via a SQLite advisory lock (`BEGIN IMMEDIATE` on a one-row `scheduler_lock`); a stale second instance fails to acquire and exits; lease expiry treats a stale holder's tasks as dead (§19)."

This text is in §8, which describes the **controller** — the reconcile loop that does not exist until P3.

**P1 roadmap (line 817) — Validation criteria:**
> "stale-lock rejection"

This tests the lock *primitive* (acquire, reject second acquirer, release, clear stale lock), not its integration into the repository layer. The test suite exercises the primitive directly via `test_phase1_acceptance.py::TestStaleLockRejection`.

**P3 roadmap (line 819):**
> "controller (§8), scheduler with `ADMIT_TASK`, `apply_intent` validators, retries, invalidation, **single-writer lock**"

The single-writer lock is explicitly listed as a P3 deliverable, alongside the controller and scheduler — the components that would acquire and enforce it.

**§18 T1 row (line 729):**
> "T1 Controller / validators / gateway | trusted | single-writer lock, deterministic code, tests"

The lock is listed under the **controller** trust boundary, not the persistence/repository boundary.

## Decision

**Outcome (a): Dormant-by-design for P1.**

The `scheduler_lock` advisory lock is a **dormant primitive** during Phase 1. It is reserved for Phase 3+ multi-controller-instance operation, where it prevents two controller processes from acting on the same project simultaneously. During Phase 1, the sole mutual-exclusion mechanism is SQLite's own `BEGIN IMMEDIATE` transaction exclusivity, which provides a real single-process guarantee: only one connection can hold a write transaction at a time, and all other writers block (via `busy_timeout`) until it commits.

The lock is **intentionally not wired** into the repository write path because:

1. **No controller exists in P1.** The controller (§8) is a P3 deliverable. The lock is the controller's mechanism for multi-instance fencing, not the repository's mechanism for transactional integrity — `BEGIN IMMEDIATE` already provides that.

2. **P1 has a single writer.** The test suite and any P1-era caller operate in a single process. The lock would add overhead without solving a problem that exists in P1's scope.

3. **Generation fencing (§19/§20) is explicitly P3+.** The lock's full value (preventing a stale controller from acting after a successor takes over) requires generation counters and session rows — all P3 deliverables. Wiring the lock without those would be a half-implementation that adds complexity without the safety property it's designed for.

4. **The P1 "stale-lock rejection" criterion is already satisfied** by the existing tests that exercise the primitive directly.

## Consequences

- `acquire_writer_lock` and `release_writer_lock` remain **production-available primitives** with no callers outside tests. This is intentional, not an oversight.
- Any future Phase 2 work that introduces a multi-connection scenario must evaluate whether to wire the lock — that decision belongs to the Phase 2/3 design, not to this IDR.
- The `force` parameter was removed from `release_writer_lock` in Part 1 of the remediation — the function unconditionally deletes the lock row, and ownership tracking is the caller's responsibility. This is correct: the caller (a future controller) decides whether it owns the lock before calling release.
