# IDR-009: Hashing Algorithm — SHA-256

**Status:** Decided (Phase 1)
**Date:** 2026-08-10
**Decides for:** Cryptographic content hash for artifact identity and dedup.

## Context

v3 §14: content hashes for tamper detection. v3 §16.1: content-addressed
artifacts. Phase 1 req §13: hash from canonical bytes, not filename/path.

## Decision

**SHA-256** (FIPS 180-4, via `hashlib.sha256`).

### Why SHA-256
- Available in the Python standard library (no dependency).
- Cryptographic collision resistance (128-bit) — no collision risk at any
  practical scale.
- Widely supported, well-understood, vetted.
- 64-character hex string is manageable as a path component.

### Canonical content
- The hash is computed over the **exact bytes** of the artifact content.
- For text artifacts, the caller must canonicalize (e.g., UTF-8 encode,
  normalize line endings to LF) before hashing if cross-platform reproducibility
  is required. The store does not modify content before hashing.
- The hash is **not** computed over: filename, filesystem path, timestamps,
  permissions, or any metadata. Content identity = hash(content bytes) only.

### Dedup
- Two artifacts with identical content produce the same hash → same storage
  path → dedup. The DB `artifacts` table enforces `UNIQUE(content_hash)` —
  a second write with the same hash returns the existing artifact_id.

### Spec/idempotency hashing
- Task `idempotency_key` is also a SHA-256 hash — of the canonical
  serialization of the task's spec + inputs. Same content → same key →
  the intent gateway rejects duplicate execution.

## Revisions

None.
