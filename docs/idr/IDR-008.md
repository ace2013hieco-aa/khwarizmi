# IDR-008: Artifact Storage Layout — Content-Addressed Filesystem

**Status:** Decided (Phase 1)
**Date:** 2026-08-10
**Decides for:** How artifact content is stored on the filesystem.

## Context

v3 §16.1: artifacts are content-addressed, immutable once committed.
v3 §16.3: authoritative evidence never GC'd. v3 §14: content hashes for
tamper detection. Phase 1 req §11-13: filesystem-backed, content-addressed,
content hash from canonical bytes (not filename/path/timestamp).

## Decision

**Sharded content-addressed layout** under the configured artifact root:

```
artifacts/
  └── <first 2 hex chars of SHA-256>/
      └── <next 2 hex chars>/
          └── <full 64-char SHA-256>
```

Example: `artifacts/ab/cd/abcdef1234567890...`

### Why sharding
- A flat directory with thousands of artifacts degrades filesystem performance.
- 2+2 hex char sharding gives 256×256 = 65,536 leaf directories — bounded
  even for very large artifact stores.

### Content vs metadata
- **Content** lives on the filesystem (binary-safe, no SQLite blob size limits).
- **Metadata** (artifact_id, type, hash, size, producer, timestamps, provenance)
  lives in the `artifacts` table in SQLite (IDR-007).
- The DB record is the index; the filesystem object is the content.

### Immutability
- An artifact path is a pure function of its content hash. Two writes with
  identical content land on the same path (dedup).
- No overwrite path exists in the API. A "new version" is a new content hash
  → a new path → a new artifact_id (v3 §12).
- Filesystem permissions are set read-only after write where the OS supports it.

### Orphaned artifacts
- If a DB commit fails after a filesystem write, the artifact is orphaned.
- Orphan detection: a cleanup pass (future phase) compares filesystem entries
  against the DB and removes unreferenced content.
- Phase 1: orphans are safe — they have no DB record and cannot be cited.

## Revisions

None.
