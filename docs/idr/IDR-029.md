# IDR-029: CONTRA P7 controller wiring — driving the task-bound EXTRACT acceptance path (C-tier)

**Status:** Decided — **IMPLEMENTED + TESTED** (Part 3 landed: `src/hermes/research/controller.py` + `tests/test_controller.py`, 12 golden fixtures proving acceptance criteria 1–10; suite 571 passed). Two design-to-code corrections were forced by the ratified state machine and are recorded here so the record stays authoritative: (1) the retry chain is `RUNNING → FAILED → RETRYING` — the ratified v4 §6.3 table has no direct `RUNNING → RETRYING` edge, so Decision 2's shorthand is implemented as a legal two-step via the `_retry_or_fail` helper, with `attempt` incremented atomically on `RETRYING → RUNNING` in `TaskRepository.transition_status`; (2) a one-shot (A2-03) divergence discovered at re-execution after recovery is FAILED directly (a retry would just diverge again), an explicit sub-case of the Decision 2 split. The write path it drives is IMPLEMENTED + TESTED (migration 5→6 producing-task binding, `record_extraction`, IDR-026/027); the EXTRACT template + `accept_extraction_output` are IMPLEMENTED + TESTED (IDR-028); the E01–E03 (48e60e5) and A2-01..03 (c0eeb18) audit remediations are landed.

---

## The gap this record closes

The EXTRACT pipeline is fully wired *except* the last mile: nothing in the runtime ever calls `accept_extraction_output` — no task is transitioned RUNNING→SUCCEEDED/FAILED based on a real acceptance verdict. The walking skeleton drives tasks manually with canned results (test-local, `tests/test_walking_skeleton.py`). This record designs the deterministic **C-tier controller** that executes EXTRACT tasks and commits their output through the now self-bound write path, with the recovery semantics the v6 model demands — without creating a scheduler, a second authority, a new event, or a new intent.

**No new authority:** the controller is the v6 Reconcile loop's execution surface (v6 §8 responsibilities 5–7: submit intents, recover stalled work, resume eligible work). It uses only existing primitives: `transition_status` (atomic, IDR-013), `apply_intent`/`INSERT_TASK` for admission (never direct inserts), `accept_extraction_output` for acceptance (self-bound — V6-P7-A2), and the `scheduler_lock` advisory lock (v4 §8, table exists since migration 1).

## Decisions

### Decision 1 — The controller is a deterministic single-tick loop over the existing graph

`Controller` in `src/hermes/research/controller.py` (new module, no new tables):

```
tick()      # one pass: acquire lock → discover eligible → claim → execute → commit
run()       # tick() until no eligible work remains or the run bound is reached
```

- **Discover:** `SELECT` READY tasks whose dependencies are all SUCCEEDED (the v4 §7 rule 1 — `transition_status` re-validates it atomically, so discovery is a cheap pre-filter, never the authority).
- **Claim:** `transition_status(task_id, READY → RUNNING)` — atomic (IDR-013), rejects if a dependency is not SUCCEEDED (F-10) or INVALIDATED. The claim *is* the dispatch; there is no separate scheduling table.
- **Execute + commit:** dispatch by task type (Decision 2/3).
- **No new events:** every transition already emits `TaskStatusChanged`; the acceptance itself emits none (the producing task's events + rows + §14 edges are the audit, IDR-026 Decision 4 / IDR-028 Decision 3). The controller adds zero event types.

### Decision 2 — EXTRACT execution: inject the model call, own the acceptance

```
execute_extract(controller, task):
    draft = controller.extract_fn(task)      # INJECTED C-tier model call (deterministic boundary)
    try:
        outcome = accept_extraction_output(conn, project_id, task_id, draft,
                                           extracted_by=..., reason="extract task <id> output")
        transition_status(task_id, RUNNING → SUCCEEDED, caused_by="controller")
    except ExtractionOutputRejected:
        transition_status(task_id, RUNNING → RETRYING or FAILED, caused_by="controller",
                          reason="extraction output rejected: <reasons>")
    except ExtractionTaskBindingError as exc:
        # IDR29-02: the binding error is TWO cases with DIFFERENT status
        # preconditions — never transition blindly from a status the task
        # may no longer hold.
        current = task_repo.get_status(task_id)   # re-read (atomic read)
        if current is not TaskStatus.RUNNING:
            # (a) LEASE RACE: the task already left RUNNING (that is why
            # A2-02 fired) — the task is already being handled by recovery
            # or a newer claim. Do NOT transition (the from-state check
            # would reject it anyway, IDR-013). Log + return; recovery
            # re-examines via the NO_SIGNAL ladder (Decision 4).
            controller.note(f"acceptance refused for {task_id}: "
                            f"task already {current.value}; recovery owns it")
        else:
            # (b) SOURCE/SPEC MISMATCH: the task is still RUNNING but its
            # spec or the draft is inconsistent — a genuine controller-side
            # failure. RUNNING → RETRYING or FAILED is correct here.
            transition_status(task_id, RUNNING → RETRYING or FAILED,
                              caused_by="controller",
                              reason=f"acceptance refused: {exc}")
```

- `extract_fn` is the **single injection point** for the deferred C-tier model call (IDR-028 Decision 5). The controller's contract to it: `task` (the row dict) → `ExtractionDraft` whose `source_ref` equals `task.spec.source_ref` (the binding enforces it — A2-01). A stub `extract_fn` (fixtures) or a future `ModelClient` adapter both fit; the controller never calls an LLM directly.
- `RETRYING` vs `FAILED` follows the existing retry policy (`max_retries`/`attempt` columns, PA1 R6 pattern): `attempt < max_retries` → RETRYING; else FAILED. Deterministic code decides — the model never does.
- The controller **never writes rows** — it calls `accept_extraction_output` (pipeline) which calls `record_extraction` (repository). One write path (v6 §31).

### Decision 3 — Non-EXTRACT tasks: the skeleton boundary

- `HUMAN_GATE` → `WAITING_HUMAN` (+ `HumanApprovalRequested`), resumed by human decision — the walking-skeleton semantics, promoted from test-local to controller behavior. Gates are never passed by the controller.
- **Mode check (IDR29-05):** before the first dispatch of a tick, the controller reads the project's lifecycle state + mode (v6 §6.2). If the mode is `AWAITING_HUMAN`/`PAUSED`, the tick **dispatches nothing** — any `WAITING_HUMAN` gate keeps the project in that mode, and the tick ends (returns `idle=waiting_human`). The mode is the wave-stop mechanism: there is no per-gate "stop the loop" flag; the loop stops because the mode says the project is not dispatchable. On resume (human decision), the mode returns to ACTIVE and the next tick dispatches again.
- `GATE` → deterministic verdict (the skeleton's `GatePassed` pattern). **Which gates are GATE vs AGENT_TASK (IDR29-06):** a gate is a `GATE` task iff its verdict function is deterministic and closed over state the controller can read (e.g. hypothesis precondition checks, evidence-ladder preconditions, plan-consistency checks — the task_plan.py integrity gates). Any gate whose verdict requires open-ended judgment is an `AGENT_TASK` under the profile that owns that judgment — notably the **Adversarial gate (§12) is an AGENT_TASK under the Adversary profile** (its `Critique` PASS/FAIL verdict is LLM judgment, never a deterministic `GatePassed`), with the deterministic checks (refuted-registry screen, pre-registration compliance) running as `GATE` tasks feeding it. The enumeration lives in task_plan.py (the template authority) and is out of the controller's hands: the controller dispatches what the plan says.
- Other `AGENT_TASK` (non-EXTRACT) → the skeleton's canned-success path for this slice, **with a documented boundary**: a per-kind handler hook (`task_handlers: dict[str, Callable]`) that the P3 evidence-task slices populate. A task with no handler is marked `SKIPPED`/left READY with a loud diagnostic rather than silently SUCCEEDED — fail-closed, never a fake success.

### Decision 4 — Recovery semantics (v6 §19/§20, no new primitives)

- **Crash mid-acceptance (the explicit chain — IDR29-01):** the write and the SUCCEEDED transition are separate transactions (the acceptance commit then the status commit). A crash between them leaves the task **RUNNING with rows persisted**. Discovery selects READY tasks, so a RUNNING task is *not* re-entered through the normal dispatch path — the recovery path is the lease ladder, made explicit:
  1. `touch(task_id)` heartbeat expires (no heartbeat during the crash window) → the controller's recovery pass transitions the stale RUNNING task RUNNING → `NO_SIGNAL` (per §19; the from-state is exactly RUNNING, so the atomic transition holds).
  2. Second conclusive miss → `NO_SIGNAL` → `FAILED` (per §19).
  3. Requeue: `FAILED` → `RETRYING` → `RUNNING` (per the state machine; `attempt` increments).
  4. Re-execution calls `accept_extraction_output` again. **A2-03 idempotency survives the attempt increment** because the one-shot rule is keyed on `producing_task_id` (the node id, unchanged across attempts), not on `attempt` — identical content re-accepts idempotently (rows already exist, same content hashes) → SUCCEEDED; divergent content is refused → FAILED. **No duplicate claims, no double-success, no silent continuation on a stale program.**
  - The recovery pass is part of the tick's discovery: after selecting READY work, the controller also scans RUNNING tasks whose `last_heartbeat` is stale (the §19 ladder above). A fresh heartbeat from a live worker reverts NO_SIGNAL → RUNNING and the worker's own acceptance completes normally.
- **Lease expiry:** a RUNNING task whose `last_heartbeat` is stale follows the v4 NO_SIGNAL ladder — the controller transitions NO_SIGNAL → (fresh heartbeat? RUNNING) / (second miss? FAILED) per §19. The heartbeat write is the controller's `touch(task_id)` call; the two-step liveness rule is preserved verbatim.
- **Re-dispatch after crash:** the idempotency key (content of spec+inputs, PA4) makes a duplicate `INSERT_TASK` return the existing task — the controller re-claims, never re-admits.
- **Single writer (honest scope — IDR29-03):** the controller acquires the `scheduler_lock` row (`BEGIN IMMEDIATE` on the one-row table) before a tick; a second *live* instance fails to acquire and exits. **[PA7] generation fencing is DEFERRED** — the `controller_generation` column and per-mutation generation validation (v6 §27 item 22) are a separate ratified slice before the P3 reconcile loop. **Until PA7 lands, the lock is advisory against a stale holder**: a crashed controller that did not release the lock holds it until the lease-expiry recovery pass treats its tasks as dead and the next instance re-acquires (the §19 ladder). This record therefore claims *lease-based* single-writer, **not** PA7's *generation-fenced* single-writer; v6 §28.6 is where the ratified §8 text's "every mutation path validates the caller's generation" must be marked as PA7-pending until that slice lands.

### Decision 5 — Deferred (explicitly out of scope)

- The actual C-tier `ModelClient` model call and source-reader allowlist (IDR-028 Decision 5).
- Budget-ledger charging (the gateway's `budget_check` hook — the controller calls `apply_intent` unchanged; the ledger is a later slice). **Honest status (AR-02/IDR29-04):** until the budget ledger lands, EXTRACT model calls execute *uncharged*. This record therefore claims **no bounded-autonomy property for the C-tier controller** — the controller is deterministic and auditable, but "budget-capped" is a DEFERRED claim (v6 §28.6 says so; nothing here relabels it). As a stopgap, the controller enforces a hard per-tick model-call cap (a `max_calls_per_tick` bound on `extract_fn` invocations, defaulted to a small constant, configurable) so a misbehaving caller cannot unboundedly spin the model inside one tick — a liveness floor, not a budget. The budget ledger spec itself is the P1-phase prerequisite before any PA2 "bounded continuation" claim (AR-02), and is not this record's slice.
- PA7 generation fencing + generation-scoped event cursors (v6 §27 item 22, ratification required).
- PA5 scheduled re-entries, re-extraction/staleness policy (P11+), Research Debt / Frontier / Observatory (v6 §28.6 no-future-phase-leakage).
- Reconcile-loop gaps/contradiction detection (responsibilities 3/8/9/10) — this slice is responsibilities 5–7 only.

## Contract notes

- **Acceptance is the controller's only write-adjacent call**; `record_extraction` is reachable only through it in production (the repository primitive remains public for the write-path fixtures, but no runtime path calls it directly — the A2-01 binding makes even a bare call task-validated).
- **No task appears outside `apply_intent`/`INSERT_TASK`** (v6 §7 rule 2); the controller never creates tasks.
- **Human gates cannot be bypassed** (v6 §28.5, §12): the controller sends gates to `WAITING_HUMAN` and stops its wave; compilation, ranking, and acceptance are never approval.
- **`extracted_by`** is supplied by the controller as the task's C-tier model ref (the task's `model_ref`-style provenance, advisory — A2-04's deferred dereference applies when a model registry lands).

## Acceptance criteria for the future Part 3 fixtures

1. A READY EXTRACT task with SUCCEEDED dependencies is claimed, executed, accepted, and lands SUCCEEDED; rows + links + §14 edges exist; event delta = only `TaskStatusChanged` (+ `IntentApplied`/`TaskCreated` at admission) — no new type.
2. An INVALID extraction output → RETRYING (attempts remain) or FAILED (exhausted), with 0 rows/links/edges (no partial write).
3. Crash between acceptance and SUCCEEDED → **the explicit recovery chain (IDR29-01)**: stale RUNNING → NO_SIGNAL → second miss → FAILED → RETRYING → RUNNING (attempt increments) → re-acceptance idempotent (A2-03 identical-content rule, keyed on `producing_task_id` not `attempt`), exactly one claim set, task SUCCEEDED. The fixture must assert the attempt increment does NOT break one-shot.
4. A RUNNING task whose lease expired → NO_SIGNAL → (fresh heartbeat → RUNNING) / (second miss → FAILED); no acceptance from a non-RUNNING task (A2-02).
5. Divergent re-execution of the same task → refused (A2-03), task FAILED, no second output.
6. `extract_fn` returning a draft whose `source_ref` ≠ `task.spec.source_ref` → `ExtractionTaskBindingError`; the task is still RUNNING → the controller transitions it RUNNING → RETRYING/FAILED, 0 rows (case b of the Decision 2 split). A lease-race binding error (task already left RUNNING) → the controller does NOT transition (case a), logs, and recovery owns the task (IDR29-02).
7. Second controller instance fails the `scheduler_lock` and exits (no interleaved execution).
8. HUMAN_GATE tasks reach `WAITING_HUMAN` and are never auto-passed; the mode check (IDR29-05) leaves the project `AWAITING_HUMAN` and the next tick dispatches nothing until the human decision returns the mode to ACTIVE.
9. Non-EXTRACT AGENT_TASK with no handler → fail-closed diagnostic (never silent SUCCEEDED).
10. Re-run of the whole sequence on the same db is idempotent (no duplicate tasks, events, rows, or edges).
