# IDR-045: Plan Admission Pass + Intent Provenance

**Status:** Decided + implemented + tested
**Date:** 2026-09-29
**Decides for:** How a compiled ResearchProgram becomes a running task graph (D1, plan-once) and how the journal records who proposed an intent (D2, additive provenance).

## Context

The system can stop at human gates but cannot yet run a plan. `task_plan.py`
(279 lines, pure, no writes) projects a compiled `ResearchProgram` into a
project-wide DAG: `hypothesis` HUMAN_GATE, then `pre_compute` HUMAN_GATE, then
integrity GATEs, then one RESEARCHER AGENT_TASK per evidence requirement, then a
`pre_live` HUMAN_GATE dependent on the chain and on all evidence tasks. No
non-test code called any `task_plan` function. `ADMIT_TASK` and `INSERT_TASK`
share one validator (`_validate_insert_task` at `gateway.py:3882`); they differ
only in the role gate (`INSERT_TASK` is `llm_proposable`, `ADMIT_TASK` is
`internal_only` / DETERMINISTIC-only). The gateway header said "the scheduler
that proposes it is P3-general-runtime, deferred" (`gateway.py:6`). Provenance
was ambiguous: the controller emitted `director_only` kinds as
`proposed_by="DIRECTOR"` at `controller.py:1123/1188`, so a journal DIRECTOR row
did not prove a director outside the controller; model-side provenance was
absent from the journal (`model_ref`/`extracted_by`/prompt lineage all zero
hits in `src/`). Two distinct gaps follow. D1: no production path admits a plan.
D2: the record of who proposed an intent cannot distinguish deterministic code
from a model, and cannot carry model/prompt lineage.

The draft `IDR-045-plan-admission-and-intent-provenance.md` v1.1 plus
ratification `D1-A, D2-A, Q1=plan-once, Q7=keyed-otherwise`, read-only evidence
`idr-045/qpass-narrow@e077898:docs/IDR45-Q37-evidence.md`, and adversarial
audit `idr-045/audit5@92ba005:docs/IDR45-audit5.md` (PASS WITH CONDITIONS
C1-C6) are the design inputs. Baseline `main@c2c8fa9`.

Follow-ons (each needs its own record; listed so nothing is silently assumed):
run envelope (task/depth/time/cost caps, fan-out bound on researcher
`INSERT_TASK` — interim per-tick admission cap noted in audit5 §3 but not
shipped here); lease horizon per task; FAILED-dependent stall handling;
REPORTING→COMPLETED lifecycle driver; reasoning-trace artifacts (4 KiB cap —
trace text must live in content-addressed artifacts referenced by hash).

## Constraints

- Single mutation path P1: every durable task row through `apply_intent`
  (`gateway.py:3961`), never `TaskRepository.create` from orchestration, no
  direct SQL mutation outside certified transaction boundaries.
- Append-only journal / no DELETE in `src/` (beyond `scheduler_lock`);
  head-only supersession (a second supersede link on one row is refused).
- Determinism owns control; models behind ports, never authorities.
- Project isolation; lease-fenced single writer; content-hash identity;
  N1/N9 fencing; bounded payloads (4 KiB).
- No new intent kind / event type / table beyond D2's six additive provenance
  fields and one repository read helper (`D2 fields` are columns on the
  `Intent` dataclass, not new tables).
- Envelope / lease / stall / lifecycle / trace stay out (follow-ons, untouched).

## Decisions

### D1 — Plan Admission Pass

1. **Admission point:** one controller pass `plan_admission_pass`, called from
   `tick()` as a hardcoded call (no registry — same precedent as every other
   tick pass) **after** the mode self-heal returns ACTIVE and **before** the
   evidence-ladder / dispatch passes, so plan tasks are committed as PENDING
   before the dispatch pass scans for eligible work. Whole tick is under the
   generation-fenced scheduler lease.

   (Corrected 2026-09-29 by MERGE-AUDIT-045 F1: this clause previously read
   "so plan tasks exist as PENDING **when readiness is computed**". `tick()` has
   no readiness computation — `readiness` occurs exactly once in `controller.py`,
   in this record's own predecessor comment, and otherwise only as a standalone
   helper in `core/graph.py`. The ordering is justified by the dispatch scan,
   which is real; the "readiness" mechanism was not.)

2. **Eligibility = filtered head C1:** the project's primary head is
   `MAX(version) WHERE parent_program_id IS NULL`. In production this is the
   **inline filtered query** `SELECT … WHERE project_id=? AND
   parent_program_id IS NULL ORDER BY version DESC LIMIT 1` inside
   `controller.py:_plan_admission_pass`.
   `ResearchProgramRepository.current_primary(project_id)`
   (`repositories.py:1711`) expresses the same projection and is exercised by
   the IDR-045 test suite, but it has **no production caller** — the controller
   does not route through it. Never the unfiltered `current()` /
   `_program_head_id`. A B3C parallel-regime-test child (`parent_program_id` not
   null, `version = max+1` alongside) never becomes the primary head and never
   steals plan admission (keyed-otherwise, Q7). Eligibility additionally
   requires: the head exists, is parseable via `_research_program_row_to_dict` +
   `program_from_dict`, is a compiler-derived program (its
   `evidence_requirements` re-derive from its `hypotheses` via
   `derive_program_obligations` — prevents synthetic q02 fixtures from being
   admitted), and `build_task_plan` does not raise. Every one of these
   ineligibility outcomes records a note (D1.7); none is a silent skip.

   (Corrected 2026-09-29 by MERGE-AUDIT-045 F4: this clause previously led with
   `current_primary` as *the* implementation, which overstated it — and
   `ROADMAP.md` repeated that overclaim. The filtered-head semantics themselves
   (C1/Q7) are unaffected and hold.)

   **Known gap, not closed here (F3):** the compiler-derived check compares only
   `evidence_requirements`; `derive_program_obligations` also returns
   `gate_requirements`, and `task_plan.build_task_plan` selects the plan's gates
   from `program.gate_requirements`. A row whose `gate_requirements` diverged
   from its hypotheses would therefore produce a different admitted DAG without
   being caught. Repository writes validate both
   (`repositories.py:1376-1379`), so only hand-written rows are exposed — which
   is precisely what this fence exists to guard. Fix is one clause
   (`or program.gate_requirements != expected_gates`); it is left open here
   because eligibility semantics are outside the scope of the merge blockers.

3. **Admission mechanism:** `build_task_plan` + `plan_to_payloads` → per-payload
   `apply_intent` loop as
   `Intent(kind=ADMIT_TASK, proposed_by="DETERMINISTIC", origin_kind="deterministic",
   origin_ref="plan_admission_pass")` (D1 intent shape + D2 provenance).
   `ADMIT_TASK` / `DETERMINISTIC` only (P4 structural — the gateway ROLE gate
   rejects any other pairing). Admission order is `plan.ordered` (gates, then
   evidence, then final gate) so any partial admission is dependency-prefix-closed
   (P2 — `ordered` property at `task_plan.py:86` + missing-dep `DEPENDENCY`
   rejection at `gateway.py:3920-3925`).

4. **Per-payload transactions C6:** no outer transaction wraps the loop.
   Each `apply_intent` is its own transaction (`apply_intent` at
   `gateway.py:4014` delegates without opening one; the task row is committed by
   `TaskRepository.create`, which owns its own `BEGIN`/`COMMIT`). A crash after
   k-of-n leaves k committed rows plus their `TaskCreated`/`IntentApplied`
   events; re-tick completes to n via idempotent `ADMIT_TASK`
   (`_validate_insert_task` returns `duplicate=True` for an existing `task_id`,
   no new `TaskCreated`).

5. **Supersession C2:** leave-in-place + admit-new-DAG.
   No DELETE on supersession (there is none in `src/` beyond `scheduler_lock`).
   A new head yields disjoint `task_ids` (`task_plan.py:_identity` over
   `program_id`). A tick where every plan task already exists is a no-op: the
   loop runs, each payload returns `duplicate=True`, and **no** note is emitted.
   That is what makes the C2 no-op distinguishable from a failure — under
   MERGE-AUDIT-045 §2.3 every failure path *does* record a note.

   (Corrected 2026-09-29: this clause previously called both the already-admitted
   tick and the uncompiled program an "observable no-op". Neither was
   observable — see D1.2 and D1.7.)

6. **Plan header/docstring freshness:** `gateway.py` module header (line 6)
   reads "the plan-admission scheduler (`Controller._plan_admission_pass`,
   IDR-045 D1) is the P3-general-runtime proposer". `task_plan.py:1` header +
   `plan_to_payloads` docstring name both `INSERT_TASK` (walking-skeleton /
   DIRECTOR) and `ADMIT_TASK` (controller plan-admission / DETERMINISTIC) paths.

   (Corrected 2026-09-29 by MERGE-AUDIT-045 F9: this edit was *claimed* done but
   had never been made — the header still said the ADMIT_TASK scheduler was
   "P3-general-runtime, deferred", which this change falsified. The edit has now
   actually landed.)

7. **Failure discipline (added 2026-09-29, MERGE-AUDIT-045 §2.3):** no outcome of
   the pass is swallowed. An unreadable head, an unparseable program, a
   non-compiler-derived program, an uncompilable program, a gateway
   `GatewayRejection`, and an unexpected exception from the gateway each record a
   note on `Controller.notes`. A tick that ends with any refusal additionally
   records the partial-DAG shortfall (how many of n were admitted, and the first
   few refusal codes), because the outward `TickResult` does not carry it. Notes
   are appended once per distinct condition (`_note_once`): `self._notes` is
   never cleared, so an unconditional per-tick append would grow it unbounded.

### D2 — Intent Provenance

1. **Additive optional fields on `Intent`:**
   `origin_kind` / `origin_ref` / `model_ref` / `run_id` /
   `prompt_template_version` / `charter_version`, each `str | None` with default
   `None`. D2 is additive: the 11 `Intent(` construction sites in `src/`
   (all in `controller.py`) and 186 in `tests/` remain valid unchanged (V2).
   (Corrected 2026-09-29 by MERGE-AUDIT-045 F13: the previously recorded
   "10 src + 175 test" counts were the pre-IDR-045 baseline; this change
   itself added the 11th `src/` site and its 26-test file moved `tests/` to
   186.)

2. **Per-field max lengths C5 — enforced PRE-WRITE:**
   `origin_kind` ∈ `{"deterministic","llm"}` (enum, max 13), `origin_ref` ≤64,
   `model_ref` ≤128, `run_id` ≤64, `prompt_template_version` ≤32,
   `charter_version` ≤32. Enforced at construction in `Intent.__post_init__`
   (fail-closed `ValueError`) and — for callers that reach `apply_intent`
   without the dataclass constructor — by `gateway._require_provenance_bounds`,
   called from `apply_intent` **before** the per-kind validator dispatches. An
   oversized field therefore refuses with `MALFORMED_PAYLOAD` having written
   **zero** rows, and the refusal is journalled as `IntentRejected`.

   **Corrected 2026-09-29 by MERGE-AUDIT-045 F2.** The bounds were first
   enforced in `gateway._append_audit_event`, which `apply_intent` calls *after*
   `_validate_insert_task` has already committed its row. Executed proof of the
   resulting defect: an oversized `origin_ref` (65 > 64) raised
   `GatewayRejection(MALFORMED_PAYLOAD)` while the task row was already durable
   and **no** `IntentApplied` and **no** `IntentRejected` row existed — a durable
   mutation with no journal record, reported to the caller as a refusal. That
   post-write copy has been removed; `_require_provenance_bounds` is the single
   gateway-boundary enforcement point, and it runs pre-write.

   Residual, pre-existing and unchanged by this correction: the 4 KiB
   `validate_payload_size` is reached only from the post-commit audit append, so
   an intent whose *whole* payload exceeds 4 KiB can still raise after its
   validator committed. That hazard class pre-dates IDR-045 and is not closed
   here. The C5 bounds no longer add to it.

   (audit5 C5 permitted "`RATIONALE` or `MALFORMED_PAYLOAD`". `RATIONALE` is not
   a rejection code in `gateway.py`; `MALFORMED_PAYLOAD` is used.)

3. **Builder semantics — only when non-default:** the audit-event payload
   literal in `gateway._append_audit_event` appends `origin_kind` etc. to the
   `IntentApplied`/`IntentRejected` payload **only when non-default**
   (`is not None` guard per field). The default-constructed payload is
   byte-identical to today: exactly `{intent_kind, proposed_by, project_id,
   justification}` — no migration, no backfill, no breaking exact-mapping
   assertion (audit5/Q-evidence proved none exists that needs this, and
   `docs/IDR45-Q37-evidence.md` §Q3 is that proof — see Q3 below).

4. **Records, never authority V1:** the gateway role gate `gateway.py:151`
   `_require_role` reads `AgentProfile(intent.proposed_by)` + the
   `IntentKind.{director_only,internal_only,llm_proposable}` partition sets
   only. No authorization decision may read `origin_*`/`model_ref`/`run_id`/…
   — the provenance fields are audit records. Structural test
   `tests/test_idr045_plan_admission_and_provenance.py:TestV1GrepGuard` enforces
   it (forbids `origin_*` reads in the role path; the only legitimate reader
   is the audit builder).

5. **Reader contract V3:** pre-existing journal rows are never backfilled.
   Readers treat missing keys as `"origin unrecorded"` (`.get("origin_kind",
   "origin unrecorded")`). Test `TestV3ReaderDefault` pins this.

6. **Not duplicative of `produced_by`/`caused_by` V5 (verified):** the 73
   `produced_by|caused_by` hits in `src/hermes/research/*.py` are labels on
   rows/events (`gateway.py:438,678` etc.), not on `Intent`.

7. **DIRECTOR sites gain provenance:** `controller.py:propose_review_actions`
   and `controller.py:propose_refutation_actions` keep `proposed_by="DIRECTOR"`
   and add `origin_kind="deterministic"` + `origin_ref` naming the digest pass
   (`propose_review_actions` / `propose_refutation_actions`). The plan admission
   pass adds `origin_kind="deterministic"` / `origin_ref="plan_admission_pass"`
   on every `ADMIT_TASK`.

8. **Helper — dict→program reconstruction:** `programs.py:program_from_dict(d)`
   reconstructs a `ResearchProgram` dataclass from the parsed row dict shape
   (`_research_program_row_to_dict`) so `controller.py:_plan_admission_pass`
   can call `build_task_plan` without a second codepath.

   `program_from_dict` is **not** the inverse of `program_to_dict`, and is not
   documented as one. `program_to_dict` omits `program_id` / `project_id`
   because they are identity metadata kept out of the content hash, so a
   round-trip through it yields `program_id == ""`. Since `task_plan._identity`
   hashes `program_id` into every plan `task_id`, an empty one would collide
   across every project and program. `program_from_dict` therefore **requires**
   non-empty `program_id` and `project_id` and raises `ValueError` rather than
   defaulting them. (Corrected 2026-09-29 by MERGE-AUDIT-045 F5; the previous
   claim that it "is the pure inverse of `program_to_dict`" was falsified by
   executed round-trip, which dropped both identity fields to `''`.)

## Relation-to-baseline

No certified invariant is weakened. Single mutation path P1, append-only
journal, determinism, project isolation, lease-fenced single writer,
content-hash identity (`fc_/_cx_/_cres_/_fx_/_retract_`), N1/N9 fencing, and
the bounded-payload discipline hold. The change introduces no new intent kind,
no new event type, and no new table: the six `Intent` provenance fields are
additive with defaults and `None`-guarded builder semantics, so prior rows'
`payload_json` stays byte-identical. The new helper
`ResearchProgramRepository.current_primary` is a read-only filtered projection
of the existing `research_programs` table, and `programs.program_from_dict` is a
pure row-dict → dataclass reconstruction at the same trust boundary — it is
**not** the inverse of `program_to_dict` and requires `program_id`/`project_id`
to be present (see D2.8 / MERGE-AUDIT-045 F5).

Envelope / lease-horizon / stall / report-aggregation / reasoning-trace remain
explicit follow-ons (untouched; each needs its own gate). The deferred
Q1 supersession item in `IDR-045-plan-admission-and-intent-provenance.md`'s
out-of-scope list is **decided** (C2) and removed from deferred. The envelope
liveness coupling (audit5 §3) remains open as a bounded-liveness follow-on,
not silently absorbed — the pass note in `docs/IDR45-audit5.md` carries forward.
The `current()` / head semantics for non-plan reads (e.g. ladder, B3 pre-check,
`completion.py:104`) are unchanged — they continue to use the unfiltered head;
only plan-admission eligibility uses the filtered primary head.
