## Context

ActionEvaluation (IDR-019) is a deterministic multidimensional comparison
library for candidate ACTIONS, consumed by the Director as advisory input.
Q-02 reconciles the surviving-idea "epistemic ROI" against that precedent:
the scalar `roi_score` model was rejected (nothing to maximize, so nothing to
Goodhart), and the surviving gap was the absence of any epistemic signal in
the controller's task-eligibility ordering (`_discover_eligible` is
`ORDER BY created_at, task_id`). The design resolved the advisory-vs-policy
ambiguity in favor of **Model B**: the ordering is deterministic control
policy, versioned, applied by the controller, and never an LLM input.

## 1. Version triple (reproducibility contract)

Every ordering result is bound to:

- `evaluator_version` — **"1.2.0"** (v1.0.0 = cost + degeneracy only;
  1.1.0 adds the obligation-fact derivation; 1.2.0 makes fulfillment
  per-requirement via stored satisfaction links).
- `policy_version` — **"task-eval-2026.1"** (the lexicographic ordering key
  and the count→level mapping; unchanged since ratification, bump on any
  policy change).
- `schema_version` — **"1"** (`TASK_ORDERING_SCHEMA_VERSION`).

Same eligible set + same version triple + same input facts ⇒ same ordering
identity (`task_ord_<sha256[:24]>`, content-derived, AC-01/AC-12). A policy
change produces a new version and a new derived ordering; historical task
executions are never silently reinterpreted. Every dispatch records the
applied `ordering_policy_version` on the `TickResult` (§9 audit trail).

## 2. Ordering key (the ratified lexicographic policy)

`TASK_ORDERING_POLICY`, a total deterministic order:

1. `DIMENSION_ORDER` levels — `evidence_gap_closure`,
   `contradiction_reduction`, `rival_discrimination`, `replication_value`,
   `frontier_value`, `coverage` — each NONE < LOW < MEDIUM < HIGH.
2. cost — LOW first, UNKNOWN last (AC-08: unknown never treated as a value).
3. `created_at` — earliest first (stored TEXT, deterministic).
4. `task_ref` — the unique PK final tie-break.

No scalar score, no weights, no dict/set iteration, no wall clock, no
`hash(random)`. Tasks whose obligation facts are unresolvable carry all-NONE
dimensions and degenerate to the `created_at`/`task_ref` baseline — the
designed failure mode (§18.4), never an error and never a heuristic fill.

## 3. Obligation-fact contract (option C: deterministic proxies, v1.2)

`task_obligations.py` (pure: imports only the shared `DimensionLevel` from
evaluation; no SQL/persistence/LLM input) derives the dimensions from the
compiled programs named in the task's gateway-validated `research_program:`
provenance refs (V6-FINAL-02), summed across linked programs, against the
project's artifact-type inventory:

| Dimension | Deterministic source | Basis ref |
|---|---|---|
| evidence_gap_closure | evidence requirements whose `required_artifacts` are not all present in the project's artifacts | `research_program:<id>:evidence_requirement:<claim_ref>` |
| rival_discrimination | UNRESOLVED rival hypotheses + discrimination requirements | `research_program:<id>:rival:<ref>` / `:discrimination:<ref>` |
| replication_value | evidence requirements on the REPLICATED rung whose artifacts are not all present | `research_program:<id>:evidence_requirement:<claim_ref>` |
| contradiction_reduction | no stored source in the current schema | — (always NONE) |
| frontier_value | no stored source in the current schema | — (always NONE) |
| coverage | no stored source in the current schema | — (always NONE) |

Ratified count→level mapping (versioned with the evaluator): total 0 → NONE;
all satisfied → LOW; exactly 1 outstanding → MEDIUM; ≥2 → HIGH.

**Satisfaction is PER-REQUIREMENT (v1.2, migration 8→9):** the class-level
approximation is gone. `program_requirement_satisfactions` stores the link
artifact → requirement (by `claim_ref`) → program, validated at admission
(IDR-038 §3.1 rules 1–4: program governed by the project; requirement
dereferences to a real evidence requirement of that program; artifact exists
in the project; artifact class is one the requirement actually requires — a
link can never claim a class the requirement does not require, and a
discrimination ref can never be recorded as an evidence satisfaction).
Idempotent via `UNIQUE(program_id, requirement_ref, artifact_id)`, append-only
(no UPDATE/DELETE path), content-derived identity, no free-form metadata (the
row IS the audit), no new event type. The derivation recomputes fulfillment
per requirement from the rows + artifact types — nothing stored is derived, a
requirement with no link is outstanding. Discrimination requirements always
count as outstanding (their satisfaction is not recorded). Malformed program
rows and entries are skipped — corrupt data is never a fact source, never a
crash (F5 on the read path, F8 on the satisfaction write path), never an
unhandled parse traceback, and is recorded on the controller's notes channel.

## 4. Controller integration (Model B)

`_dispatch_pass` orders `_discover_eligible`'s output via `_order_eligible`
before claiming. Eligibility (dependencies SUCCEEDED, gates, per-tick call
cap) runs FIRST and unchanged — the ordering only decides who among the
already-eligible runs first; it never admits, never overrides a gate/budget/
dependency, and never creates work. The obligation context is loaded once per
tick (project-scoped SELECTs only — read-only, inside the single-writer
lock). `enable_epistemic_ordering=False` restores the baseline `created_at`
order (the §13.8 removal switch). The only schema addition is the sanctioned
migration 8→9 table (`program_requirement_satisfactions`) in the migration
registry — no event, intent, scheduler, or authority.

## 5. Authority boundary

- The Controller decides which task runs next, per the ratified policy; Q-02
  supplies the policy only.
- The forbidden chain (LLM → "high ROI" → hidden scheduler → execution
  priority) is structurally impossible: the only input path to the ordering
  is the deterministic derivation (task state + compiled program rows +
  per-requirement satisfaction links). Spec-supplied `roi_score`/`information_gain` fields
  are invisible to the policy (fixture-proven).
- The Director surface (CandidateAction mode) and the controller surface
  (EligibleTask mode) share the same `DimensionLevel`/`CostTier`/
  `DIMENSION_ORDER` constants — one policy source, cycle-free import
  direction (evaluation imports only programs; controller → evaluation;
  task_obligations → evaluation).
