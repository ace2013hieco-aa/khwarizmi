# IDR-004: CLI Framework — stdlib `argparse`

**Status:** Decided (Phase 0)
**Date:** 2026-08-10
**Decides for:** How the `hermes` command-line interface is structured.

## Context

Foundation §7 requires an operational CLI (`hermes init`, `doctor`, `project`, `task`, `run`, `pause`, `resume`, `status`, `audit`) that is purely an operational surface — no business logic — with business logic remaining in Hermes modules. Foundation §4 mandates a minimal-core-dependency policy.

## Decision

Use the Python standard library's **`argparse`** module as the CLI framework, with a `main(argv)` entrypoint exported via the `[project.scripts] hermes = "hermes.cli:main"` console-script.

## Rationale

1. Stdlib: zero dependency weight; consistent with foundation §4/§5.
2. Phase 0 only needs `--help`, `doctor`, and stubbed sub-commands — argparse handles this trivially.
3. The CLI boundary is intentionally thin; heavier frameworks (Click, Typer) would add complexity disproportionate to the surface.
4. A single `main(argv) -> int` makes the CLI unit-testable without subprocess overhead.

## Alternatives Considered

* **Click** — elegant, but adds a runtime dependency for no Phase-0 benefit.
* **Typer** — same dependency concern plus type-annotation coupling.
* **Rich / rich-argparse** — nice output but not needed at this stage; can be added later behind an optional extra if richer doctor output is wanted.

## Consequences

* `hermes.cli.main` is testable with `main(["doctor"])` and returns an int exit code.
* Each subcommand branches in `main`; Phase-0 unimplemented commands print "not yet implemented" and return 0.
* `hermes doctor` is the only fully-implemented subcommand in Phase 0; it probes the environment and distinguishes `AVAILABLE` / `OPTIONAL / NOT CONFIGURED` / `REQUIRED / MISSING` per foundation §10.
* If typed-option complexity grows significantly in later phases, we can revisit via an IDR.
