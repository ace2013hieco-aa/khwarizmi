# IDR-017: `invalidate()` Non-Cascade Contract — Known Deliberate Gap

**Status:** Decided (Phase 1)
**Date:** 2026-08-11
**Decides for:** The scope of `TaskRepository.invalidate()` — specifically, whether it cascades to downstream dependents or checks whether a dependent is currently `RUNNING`.

## Context

The hostile re-verification report (§C.6) noted that `TaskRepository.invalidate()` transitions a single `SUCCEEDED` task to `INVALIDATED` atomically and correctly rejects non-`SUCCEEDED` sources. It does not compute or touch downstream dependents, and nothing in the codebase checks whether a downstream dependent is `RUNNING` at the moment its dependency is invalidated.

### Relevant v4 text

**§7 rule 4 — INVALIDATED semantics:**
INVALIDATED results stay archived; a new node is created for the re-run. The full cascade behavior — invalidating downstream dependents when a source is retracted or invalidated — is described as the "eventual full behavior" per v4.

**§8 (P3 roadmap, line 819):**
The reconcile loop (§8) is assigned to P3. The reconcile loop is the component that would compute cascade invalidation: it walks the dependency graph, finds downstream dependents of an invalidated node, and transitions them to appropriate statuses.

**§7 rule 3 — Loops are re-instantiation:**
A new research iteration creates a new subgraph; the previous subgraph is preserved. The reconcile loop, not the repository, manages iteration boundaries and subgraph transitions.

## Decision

**`TaskRepository.invalidate()` is a single-task operation. It does not cascade.**

Specifically, it does not:

1. Query for downstream dependents (tasks that have this task in their `dependencies` list).
2. Transition any downstream dependent to any status.
3. Check whether a downstream dependent is currently `RUNNING`.
4. Emit any warning, log, or event about a running dependent.

The method's sole effect is: transition `task_id` from `SUCCEEDED` to `INVALIDATED` atomically, emit `TaskInvalidated` event, and return the updated task. The old result stays archived — never deleted, never overwritten.

This is a **known, deliberate, currently-open gap**, not a bug to silently fix and not something to paper over as "fine because it's deferred" without writing it down.

## Rationale

1. **Cascade requires graph traversal.** Computing "all downstream dependents of task X" requires either a recursive CTE (§14), a BFS/DFS over the dependency map, or a precomputed reverse-index. None of these exist in Phase 1.

2. **Cascade requires policy decisions.** When a downstream dependent is `RUNNING` at the moment its dependency is invalidated, the correct behavior is a design question: does the system block the invalidation? Queue it? Force the child to `FAILED`? Mark it `INVALIDATED` and let the reconcile loop handle it? Each option has different semantics for resume, idempotency, and audit trail. This is a Phase 2/3 design decision, not something to improvise.

3. **Cascade requires the reconcile loop.** The reconcile loop (§8, P3) is the component that manages task state transitions driven by external events (lease expiry, artifact changes, source retraction). It is the natural home for cascade computation because it already does deterministic graph traversal for readiness and scheduling.

4. **The current behavior is safe.** Invalidating a task without cascading leaves any running dependent in `RUNNING`. When that dependent tries to advance, its `transition_status` check will see the invalidated dependency (F-10) and reject the transition. The dependent will not silently produce results based on invalidated evidence — it will fail fast with a `DependencyError`. This is a correct, conservative behavior.

## Consequences

- `TaskRepository.invalidate()` is annotated with a code comment stating the non-cascade contract and referencing this IDR.
- A regression test pins the current behavior: a `RUNNING` dependent is untouched when its dependency is invalidated.
- Phase 2/3 work that implements cascade invalidation must update this IDR and the regression test.
- Any caller that needs cascade semantics today must implement graph traversal themselves and call `invalidate()` on each downstream node explicitly.
