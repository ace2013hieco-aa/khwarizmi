# Adversarial Review — ResearchSourceProvider Blueprint, Third Gate (post-PS2 remediation)

**Scope:** third-gate protest-stage attack on the **PS2-remediated** `hermes_researchsourceprovider_implementation_design.md` (PS-01…PS-13 and PS2-01…PS2-09 folded in) against its own contract and the second gate's claims. Method: attack exactly the four surfaces the PS2 remediation *built or rewrote* — the `NoFullText` semantics, the fetch-scoped `FetchHazardRules`, the zero-delivered aggregate matrix, and the transport-held `from None` redaction — for the same bypass/silent-failure classes, plus the adjacent text the remediation touched (the fetch driver, the spec schema, the walk's verdict mapping). The first and second gates' findings were treated as closed only where the text actually closes them; every PS3 finding below is a hole in the *PS2-remediated* text, not a re-litigation of prior rounds.

## Detail

**PS3-01 — The 404 classification precedence is undefined. (P1)**

The PS2 remediation added step 6a ("Fetch scope — `no_full_text_status` match (europepmc 404) → `NO_FULL_TEXT`") *after* step 1 ("Status check — non-200/2xx → map (404 → `VALID_NEGATIVE` for identifier lookups per the provider's spec; 429 → `THROTTLED`; 5xx → transient)"). Both rules read the same status code through the same generic evaluator, and the text never states that fetch scope overrides step 1. europepmc's clean 404 — the contract's *preferred* answer, and the case the entire fetch surface was built around — therefore has two competing classifications: as a search response it is `VALID_NEGATIVE` (a `SearchResult` with `valid_negative: true`); as a fetch response it must be `NO_FULL_TEXT` (a `NoFullText` result). If scope handling is wrong, omitted, or evaluated in the wrong order, the 404 lands in the wrong outcome class and the fetch driver's mapping table (verdict → `FetchedSource`/`NoFullText`/`FetchFailure`) is never enumerated anywhere in the document — only `NO_FULL_TEXT → NoFullText` and "real failures → `FetchFailure`" are named, leaving what a fetch-scope `VALID_NEGATIVE` or `THROTTLED` becomes to the implementer. **Fix: pin the precedence (fetch scope short-circuits step 1's 404 branch; the scope flag is a driver-set context, never inferable from the payload), and enumerate the full verdict→outcome mapping table at fetch scope** — every `HazardVerdict` class the fetch driver can receive and its outcome, with "unreachable at fetch scope" stated for the walk-only classes (`CURSOR_TRAP`, `REWRITE_SUSPECT`).

**PS3-02 — The empty-fetch-payload corner admits a silent empty artifact. (P1)**

The composite PMC check ("metadata present AND body absent → `PARTIAL_CONTENT`") has a precondition: it fires only when `metadata_marker` is present. A 200 fetch response with an empty body **and no front element** fails the precondition and matches nothing: step 6a's `required_fields` catches it *only if the spec author declared fetch-scoped required fields*, and the search-shaped `empty_body_rule` is explicitly excluded from fetch ("the search-shaped fields above do NOT apply to fetch payloads" — `empty_body_rule` is not listed as applying). The walk then has no verdict, and the fetch driver's per-source outcome logic (with no enumerated mapping, per PS3-01) falls through to `FetchedSource` — a zero-byte "full text" artifact admitted as if it were the article. A present-but-empty `<body/>` element is the same hole one step earlier: the composite checks element *presence*, so `<body/>` with zero content passes `body_required` and produces an empty artifact. **Fix: a fetch-scoped empty rule (`fetch.empty_body_rule: "treat-as-failure"` — a fetch empty body is NEVER a valid negative, unlike search), a non-emptiness check on the body element (present-but-empty == absent), and a fetch-scope fall-through rule: any fetch response with no matching verdict and no body content is `FetchFailure(EMPTY_RESULT)`, never `FetchedSource`.**

**PS3-03 — `NoFullText.reason` is free prose and the driver cannot know the cause. (P2)**

The PS2 fix makes `NoFullText` a result with `reason: str` — a free string the fetch driver writes. But the driver sees only status codes and marker hits: a 404 from europepmc is "not OA" for a normal citation-only article, "removed" for a **retracted** record, and "never existed" for a stale identifier. All three are 404s. If the driver writes "no full text available" uniformly, a retraction is recorded as a benign citation-only result, counted toward `COMPLETE`, and downstream consumers (evidence, LitKG) have no signal that the source may be withdrawn. The design also gives no rule for what the driver is allowed to assert. **Fix: structured `reason` — `no_full_text_kind ∈ {NOT_OA, REMOVED_OR_RETRACTED, NOT_FOUND}` derived only from what the response actually evidences (status, marker path), plus the evidence basis fields — and a note that a provider-declared retraction marker, where one exists, must map to `REMOVED_OR_RETRACTED`, never `NOT_OA`.** The driver never guesses *why* a status occurred beyond what the spec declares.

**PS3-04 — Aggregate polysemy: `COMPLETE` no longer means what it says. (P2)**

The PS2 fix made all-`NoFullText` batches aggregate `COMPLETE` — correct for "all sources resolved," but `COMPLETE` previously meant "all sources fetched with artifacts." Any consumer that reads only the aggregate (a task checking "did the fetch succeed?") now receives `COMPLETE` with zero artifacts and no way to distinguish "full text obtained for all" from "full text obtained for none." The outcome carries `per_source`/`no_full_text`/`failed` tuples, so the information exists — but nothing states that the aggregate alone is not an evidence-quality signal, and there is no aggregate-level count. **Fix: carry `fetched_count` and `no_full_text_count` on `FetchOutcome`, and state the reading rule: the aggregate is a resolution signal; per-source outcomes are the evidence signal; a consumer may not conclude full-text availability from the aggregate alone.**

**PS3-05 — `FetchHazardRules` lacks registration-time coherence validation. (P2)**

PS2-09 extended spec-loading validation to `count_semantics` × `counts_raw_rows` but not to the new fetch-scoped structure. `body_required: true` with no `body_marker`, `no_full_text_status` declared on a search-only provider, or `no_full_text_marker` with no `no_full_text_status` all pass registration and ship either a check that can never fire or a rule with no trigger. The fail-closed-at-registration discipline the blueprint correctly applies to count semantics must cover the fetch structure too: **spec-loading validation rejects (a) `body_required` without `body_marker`, (b) any fetch rule on a spec whose provider has no fetch surface, (c) `no_full_text_marker` without `no_full_text_status`, and (d) a `FetchHazardRules` with neither `body_required` nor `no_full_text_status` nor fetch `required_fields` (a fetch rule set that can never fire).**

**PS3-06 — The aggregate matrix still has uncovered corners. (P2)**

The PS2 matrix pins the zero-delivered cases (empty-and-down → `EMPTY`; no-provider-ran → `UNAVAILABLE`; valid-negative-only → `COMPLETE`) but the mixed corners are still open. (a) A valid-negative answer mixed with an empty topic search: the lookup was answered "no" *and* a search found nothing — `COMPLETE` (answered) or `EMPTY` (searched, found nothing)? (b) A valid-negative mixed with real results: the lookup was answered and results delivered — `COMPLETE` or `PARTIAL`? The second gate's own reasoning ("never `PARTIAL` for an answered lookup") implies (b) is `COMPLETE`, but the text only covers the valid-negative-**only** case. (c) The hint-routing corner from walk step 1: an unknown hint prefix (`xyz:…`) and the zero-routed-provider case (no adapter is routeable for the query) are not pinned — `ProviderValidationError` (bad hint, before I/O) or `UNAVAILABLE` (could not search)? **Fix: extend the contract §4.2 matrix with the valid-negative-mix rows and pin the no-routeable-adapter verdict — an unknown hint prefix is `ProviderValidationError`; a routeable-but-all-skipped fan-out is `UNAVAILABLE`.**

**PS3-07 — The `from None` discipline is stated at the raise site only. (P3)**

PS2-04 made the transport "the only component that raises provider errors" with `from None`. Three completion gaps: (a) **re-raise hops** — the blueprint allows concurrent walks ("walk concurrency is a latency choice"), and concurrent futures / `ExceptionGroup` machinery re-raise exceptions with their captured tracebacks; a generic `raise exc` at any hop re-links the chain and can surface the raw urllib error (whose `str()` contains the URL). The `from None` rule must be stated as holding at every hop, including future wrappers. (b) **`RedactionError`** — it is raised by `redact.py`, which is holding the raw params at that moment; its message must name the offending parameter, never its value (the one exception class raised while raw credentials are in scope). (c) **`redact_url`** covers query params; a credential embedded in a path segment (some providers use `/{token}/…` routes) needs the alias scan applied to path segments too. All three are one-line contract completions.

**PS3-08 — `no_full_text_marker` vs `no_full_text_status` precedence is unstated. (P3)**

The spec declares both an optional status (`no_full_text_status: 404`) and an optional body marker (`no_full_text_marker`). A 404 whose body contains a marker saying "temporarily unavailable" vs "no full text" can answer either way, and the interaction of fetch-scoped `required_fields` with the `body_required` composite is also undefined (a 200 failing fetch `required_fields` is `MALFORMED_200` — but what if the composite precondition is also satisfied?). **Fix: pin the evaluation order at fetch scope — marker evidence wins over status alone when present; `MALFORMED_200` (required-fields failure) dominates `PARTIAL_CONTENT` (composite) — and record both in the verdict's `detected_by`.**

## What survives

The full spine holds under the third pass: the only-entry-point invariant, the thin-adapter four-hook skeleton under one provider-agnostic driver, hazards-as-data with the generic evaluator, the fixed allowlist fan-out order, the full-request-state fingerprint with fail-closed replay, skip-and-count row policy, `required_fields` drift sentinel, recorder-boundary redaction with the transport-held policy, the raw-vs-delivered count naming, serial fetch order, the fetch-shaped log, and the zero-delivered matrix's three pinned cases. The PS3 findings are **precision gaps in the exact text the PS2 remediation wrote** — precedence, fall-through, structure-of-reason, and matrix corners — not structural collapse. Every fix lands in the same blueprint sections and the contract where it wins (PS3-03, PS3-04, PS3-06).

## Overall verdict: **MERGE WITH REMEDIATION (third round).**

The second gate's P1s are genuinely closed — `NoFullText`, `FetchHazardRules`, and the matrix exist and are load-bearing. But the surfaces the PS2 remediation built carry their own P1-class holes: the 404 classification precedence between the global status check and the fetch-scoped rule is undefined (PS3-01), and the empty-fetch-payload corner can silently admit a zero-byte artifact as fetched full text (PS3-02). The `NoFullText` reason needs structure so a retraction is never masked as "not OA" (PS3-03), the aggregate's polysemy needs counts and a reading rule (PS3-04), the fetch spec needs registration validation (PS3-05), the matrix needs its mixed corners pinned (PS3-06), and the redaction chain needs its hop-level completions (PS3-07/08). All eight map to concrete design-text changes in the same blueprint/contract modules. The standing condition before §27 item 55 ratification and Part 3 is a fourth gate against this text — or acceptance with the PS3 dispositions folded in.
