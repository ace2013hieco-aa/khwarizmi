# Adversarial Review — Step-4 limiter/transport design, third gate (post-RT2 fold-in)

**Scope:** protest-stage attack on ONLY the four surfaces the RT2 fold-in fixed, against the remediated §6.1/§6.1a text (blueprint `hermes_researchsourceprovider_implementation_design.md`) + contract §6 — (1) the status deferral (RT2-01 — the transport raises only for transport-level failures, all HTTP statuses to `evaluate_hazards`), (2) the `False` reservation + `ADMISSION_WAIT_BOUND` (RT2-02), (3) the before-the-try return check (RT2-03), (4) the evaluator-hosted content-type with status dominance (RT2-04). Method: treat the RT2 dispositions as settled only where the remediated text actually enforces them; probe each surface for the SAME bypass/silent-misclassification classes (a verdict pre-empted, a signal domain conflated, a note with no carrier, an ordering gap). Every finding quotes the remediated text it contradicts or leaves open, and is verified against the shipped driver's shape (paginate.py `_fetch_page` — acquire outside the try, the `except Exception` catch-all, the walk loop's failure_class mapping) and the shipped `base.py` Protocol (`ProviderRateLimiter.acquire -> None`, `TransportResponse` fields). No limiter code exists yet — design-text review, the WS/RT/RT2-review precedent.

## Detail

**RT3-01 — The size cap keeps a transport raise that pre-empts statuses. (P2)**

§6.1a: "timeout/connection → `TransientProviderError(hazard_class="TIMEOUT")`…; size cap → `PARTIAL_CONTENT`" (the transport raises) and "**ALL HTTP statuses are deferred to `evaluate_hazards` — the transport NEVER raises on a status code**". But the size-cap raise is not status-conditional: the transport reads the body (it must, to know the size), and if an oversized body arrives with a 429 (a broken-gateway error page, oversized) or a lookup 404, the transport raises `PARTIAL_CONTENT` (a PERMANENT class) BEFORE `evaluate_hazards` ever sees the status — a throttled/answered response becomes a permanent schema verdict. This is exactly the dominance class RT2-01 closed for statuses, reopened by the size rule. **Fix: split the two size concepts — (a) the streaming download-abort (genuinely transport-level) fires only when the status is 2xx (or the abort is classed as the transient/`PARTIAL_CONTENT` it is, with status evidence dominating downstream); (b) the completed-body size check moves into the evaluator (like the content-type check — the body length travels in `HazardContext`) so it runs after the status verdicts.**

**RT3-02 — The admission-wait expiry keeps the daily cap's signal AND its no-retry. (P2)**

§6.1: "a **daily-cap hit returns `False`** … so **no retry**" and "on the pathological expiry, `acquire` returns `False` as a THROTTLED-class admission failure… the verdict is `SHORTFALL(cause=THROTTLED)` for both". RT2-02's own fix said "reserve `False` for the daily cap only… never the same signal as the cap". The fold-in took the "very long defined bound" leg (the wait is bounded, the cause is note-distinguished) but the expiry still returns `False` and the driver's uniform mapping (`if not limiter.acquire(...): return None, "THROTTLED", "THROTTLED"` — RT2-03's pinned shape) applies the daily cap's **no-retry** to a **transient** condition: a concurrent walk holding the slot frees it at the request's end (per-request release, WK3-01), so a walk whose first-page acquire waited 60s and expired ends `SHORTFALL(cause=THROTTLED)` — aggregate `UNAVAILABLE` — on a contention that cleared moments later. **Fix: the admission-expiry must be RETRYABLE — the driver's retry loop re-calls `acquire` on the next attempt (a subsequent acquire may succeed) — while the daily cap stays no-retry; that requires the cause BEFORE the mapping (RT3-03).**

**RT3-03 — The cause notes have no carrier. (P2)**

§6.1: "The two `False` causes are distinguished in the outcome's notes (`daily_cap_exhausted=true` vs `admission_wait_expired=true`)". The API is `acquire(provider) -> bool` — the driver sees `False` and NOTHING else; the limiter has no accessor and no write path into the outcome's notes. The distinguishing note is unwritable. **Fix: keep `-> bool` and add a Protocol accessor the driver reads after a `False` — `limiter.last_denial_reason(provider) -> str` (`"daily_cap_exhausted"` | `"admission_wait_expired"`) — which the driver appends to the outcome's notes; this ALSO supplies the cause RT3-02 needs before the mapping (the driver can branch: cap → no retry; admission expiry → the retry loop re-acquires).**

**RT3-04 — The content-type slot in the fixed order is underspecified. (P3)**

§6.1a: "the check runs AFTER the status-based verdicts". The evaluator's fixed order (module docstring) is: status (fetch-scope 404 precedence) → throttle → error-field + markers → required-fields drift → empty-body → rewrite → advisory → fetch step 6a. "After the status-based verdicts" pins the content-type check after step 1 — but the **drift sentinel** (a 200 whose shape fails `required_fields`), the **empty-body rule**, and the **fetch composites** (retraction → `REMOVED_OR_RETRACTED`, `no_full_text`) all produce verdicts the mismatch must not pre-empt (a retracted article served with an unexpected content-type must stay `REMOVED_OR_RETRACTED`, never `MALFORMED_200`). Pin the exact slot (e.g., after the drift sentinel, before the fetch composites — or last, as an advisory-then-hard rule).

**RT3-05 — Protocol drift. (P3)**

`base.py`'s shipped `ProviderRateLimiter` Protocol still declares `def acquire(self, provider: str) -> None`; §6.1 pins `-> bool` and RT2-03's code shape checks the return. The Protocol signature change, the shipped `walk()` call site, and the test fakes (`FakeLimiter`) are step-4 implementation edits — the fold-in should list them explicitly, or the step-4 driver edit won't typecheck against the shipped Protocol.

## What survives

The RT2 fixes hold exactly for the forms their text states: the status deferral is structurally sound for the CLASSES it names (404/429 reach the evaluator — the answered-lookup and Retry-After paths survive); the before-the-try check is the right shape (no release after a `False`); the evaluator-hosted content-type closes the note-carrier problem for the allowlist path (the evaluator owns notes); the catch-all re-raise is correct. The five findings are the residual pre-emption (size), the residual conflation (expiry vs cap), the missing carrier (cause notes), and two ordering/drift pins — all in the same boundary the first two gates found: the limiter/transport ↔ evaluator interface.

## Overall verdict: **MERGE WITH REMEDIATION (third gate).**

**RT3-01/02/03** are P2s the step-4 implementation must carry: the size rule split (status-conditional abort + evaluator-side body check), the admission-expiry retryability (a transient contention must not end the walk with the cap's no-retry), and the `last_denial_reason` accessor that carries the cause notes AND enables the RT3-02 retry branch. **RT3-04/05** are P3 pins for the fixture plan (the content-type slot, the Protocol signature change). All five land in §6.1/§6.1a + contract §6 + the `base.py` Protocol — no redesign, no new components — and the fold-in is the standing condition before `ratelimit.py`/`http.py` are written.
